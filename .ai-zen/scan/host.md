### 结论（一句话）

骨架是对的（`deliver` 只判「在不在、活不活」+ 两个 `mayStart` 创建者、四格只由 `statusOfAgent` 合成、`message.list` 内存优先、交接换记忆一个 `tx`、阈值/开关/血缘只在会话行上读），但**三处硬伤 + 一大片白跑的东西**：挂着的交接题遇上死对话会把这段对话**永久卡死**；交接回滚拿「记忆长度水位」当「这一趟写了多少」当判据，会把交接期间**已经落地进来的话静默抹掉**（而它们按设计又从未落库）；`AgentRegistry` 里那条状态观察通道（`observeState` / `onState` / `AgentStateEvent` + 每 agent 4 个 core 订阅 + `from/to` 合成）**全仓零消费者**，它既是白跑的代码，也是「状态合成第二处」的唯一现场。

### 没把握的地方

1. **A1 的「零消费者」是静态 grep 的结论**（`packages/*/src`，排除 `dist`）。`runtime/index.ts:45` 仍然导出 `AgentStateEvent`，仓库外的使用者（桌面端）理论上能订阅 —— 但 `onState` 是 `ChatRunnerOptions` 的构造参数、而 `app.ts` 造 `ChatRunner` 时没传，所以**宿主进程内**这条通道一定是空转的。删不删取决于「宿主之后想不想把那一格广播给别人」，这一条得接线的负责人点头。
2. **A10 / A14 的「谁读它」**：`around` / `includeHidden` / `QuestionState.expired|cancelled` 在仓库内零生产消费者，但桌面端不在本仓库。`wire/methods.ts:687-690` 明确点了消费者（PLAN W4 的搜索跳转），所以我按「契约留、但要有人点头」处理，没有建议立刻删。
3. **C2 的严重度取决于界面**：`wire/states.ts:149-155` 说交接期间「输入框拦住、只留中断按钮」，若客户端真的拦住，普通用户就走不到那条路；但**平级会话的 `postMessage`**（`services/PeerSessionService.ts:386`，投递不看关系）与任何不拦的客户端都能在交接窗口里投话，所以这条窗口是开的。我没有跑端到端复现（那要写真数据 + 真模型），只按代码路径推。
4. **C1 的死锁没写复现用例**：它是「`status === "dead"` + `pending` 且 `blocking` 的题」的组合。我核过 `QuestionService.askHandoff` 里 `blocking: input.blocking ?? true`（`:385`），也核过 `ChatRunner.state()` 在无 agent 时报 `dead`（`runtime/ChatRunner.ts:1690-1695`）；但「进程重启后那道题还在」这一点只读了 `QuestionRepository` 的持久化，没有实际起进程验证。
5. **`ChatRunner.ensureAgent` 的兜底分支**（`runtime/ChatRunner.ts:1847-1886`，「活着但不合用」那一支）：注释说它「不再是正路」但仍然留着。我没能构造出一个只有它能兜住的真实场景（换模型/换档位已经先退役了），所以没进 A 清单 —— 它可能是一段可以删的防御分支，也可能兜住我没看到的入口。
6. **`deliver` 与退役之间的窄竞态**：`deliver` 先 `agents.get` 拿到 agent、再 `bridgeFor` 建桥；两步之间该 agent 若被 `retire`（不是 kill），投递会落进一个「已不登记但还活着」的实例，`state()` 报 `dead` 而消息照样被处理。读代码看是这样，但我没有构造用例确认 core 的循环会不会真的取走它，故未列类。
7. **`B10` 三处判据里哪一种是「对」的**：`ConversationService.ts:1084-1089` 明确论证了「暂停也算空闲」（换模型不打岔在途那批），而 `QuestionService` 的论证是「题答完会当场开始交接，所以不能暂停」。两个理由都成立 —— 这可能是**两个不同的判断**被同一个词（空闲）表达，而不是单纯的不一致。我按 B 列，但承认它也可能该拆成两个名字。
8. **`storage/migrations.ts` 的 v4 默认值**：我按「升级用户会静默自压」定性为 D。若产品侧认定「老会话本来就没有『问一次』的记忆，选开更省事」，那 D1 就只是注释口径要统一（把 `app.ts:1105` 那句「关是常态」改掉），而不是缺陷。这一条要用户拍。
