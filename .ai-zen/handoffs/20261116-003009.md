## 🎯 Task Goal

用户这一阶段的真实意图，按他定的顺序：

1. **inbox 是 core 的一等输入口**：`deliver` 与 `send` 平级，绝不两段 run 并跑，**整批插入多条 user message**（不是一条一轮）。
2. **agent 常驻**：一段对话一个 agent，跨轮复用；存活管理显式、手动、无计时器、无自动回收。
3. **会话之间能通信**：一段对话里的模型能开另一段会话说活，结果自动推回并**唤醒**它（唤醒 ≠ 复活，两个词分开）。
4. **压缩自动化**：派生会话（平级会话开出来的）一律自动压缩、不弹问；会话上留 `auto`/`manual` 标记。
5. **代码尽可能简洁**：不为边角写代码；「用复杂方法解决简单问题」是治理对象。

验收口径：状态自洽 + 代码短 + 用户可见行为对；不要「覆盖所有情况」。

## 🧠 Key Decisions

- **inbox 留在 agent 里，agent 改成常驻**。旧 `actor.md` / `actor-mmvp.md` 那套（地址 + 邮箱 + 循环 + 网络文件）被用户否掉：太复杂，且高/低优先级难实现。`core` 的 `inbox` 已有 `priority` + 一处取件点，直接用。
- **唤醒 vs 复活**（用户点出来的）：唤醒 = agent 活着、有 inbox 内容 → 起一段；复活 = agent 不在 → 从库里历史重新装配。`deliver` 只唤醒，复活走 `agents.acquire`；两个词不许混。
- **判断权在宿主，不在 core**：因为 agent 跑完即弃的时代 core 里根本没有「空闲可唤醒的对象」。现在的形状是 `ChatRunner.deliver` 三态（running / idle / settling）+ 会话级 waitlist，把落后窗口也一起关掉。**`inbox-first-class` 那份 plan 主张「宿主不判在不在跑」，与实际相反 —— 那份文档已删除，别再照它做。**
- **配置改动不是生命周期事件**：`Scope.config` 从构造快照改成现读，`refresh()` 连 config 一起重读；MCP 按定义对账断旧连接。所以「改配置」永不重建 Scope；受影响 agent 由 `AgentRegistry.invalidate` 换掉（否则模型客户端还是旧的）。
- **没有空闲回收、没有引用计数、没有计时器**：实例活着就是有人显式持有它。退出判据只剩「无连接 + 无在跑轮次」。代价：宿主不再因空闲自行退出，脏进程靠这条判据兜。
- **回投跟着每一次段结算**（不是跟着 `create_session` 那一次）：否则 `send_to_session` 叫起来的段结果永远回不来。循环风险靠「深度一层 + 父对话不在 `records` 里」自然收住，不做预算/熔断。
- **文档只有两份**：`agents/PRD.md`（需求/决策/裁定/契约/没做）+ `agents/PLAN.md`（结构/生命周期/时序/落点/波次/欠账）。历史存档（`.ai-zen/handoffs`、`.ai-zen/audits`、`CHANGELOG`）不许改写。
- **踩过的坑（别重复）**：
  1. `grep ... | head` 会把后半个仓的命中截掉 —— 我曾据此断言「cli 不读 `recycledWorkspaceIds`」，结果 cli 编译红了（后来 `889f22f` 修的）。**判定「无人使用」时不要接 `head`**。
  2. `npx vitest` 会退到 npx 缓存里那份、读不到配置，计数翻倍。永远用 `./node_modules/.bin/vitest`。
  3. `pkill -f "aizen-smoke"` 会匹配到自己那条命令行（把自己的 shell 杀了）。停进程用 `ss -ltnp` 取 pid。
  4. shell 里 `cd X && ... &` 会把整个 `cd &&` 一起后台；用 spawn 的 `cwd` 参数。
  5. dash 不支持 `mkdir {a,b}` 花括号展开，会造出字面目录名 `{a,b}`。
  6. host 的类型来自 `packages/host/dist`：改了 core 或 sdk 的 `.d.ts` 要先 `cd packages/{core,sdk} && ./node_modules/.bin/tsc`，否则 host 的 tsc 对着旧声明报错。
  7. e2e 前要先 `npm run build` 刷 dist，否则 `serve.process.test.ts` 的子进程启动即崩。
  8. 派单时别把自己的转述当现状：实施者已经三次纠正我的任务书（`flushInbox` 只有一个调用方、`AutoMigratePlugin` 早就装着、`pendingDispose`/`deliverAll` 名字对不上）。
