## 🧠 Key Decisions

以下是这轮敲定的、**不要重开**的口径（理由都写在 `CORE.md` 对应小节的「为什么」里）：

- **死活五个动作**：`start` / `stop`（关门、存量走完、排空才死）/ `abort`（暂停，掐在途 IO）/ `resume`（显式开关，只置意愿）/ `kill`（硬着陆、存量作废）。曾定过「暂停靠收到用户事件自动解除」，用户否掉：一个 agent 不该因为别人投了东西就自己动起来。
- **暂停中 `stop`** = 不跑 + 关门，存量作废（用户选 b）。
- **一次性**：死了就死透，复活 = 新建；关门后再 `push` **抛 `AgentError("closed")`**，不静默丢（用户选 b：外面负责处理错误）。
- **inbox 一条队列 + 谓词**，不是两条道。原因：两条道要合并就得加递增序号还原先后；一条队列顺序天然。**`.filter()` 这个名字被否**（撞 TC39 异步迭代器辅助方法），改为 `takeAll(filterCallback?)`（同步取干）+ `asTakeAll()`（视图，一批一批）。
- **状态只给三格**：忙 / 闲 / 暂停。六态（连首字/在想/在输出/拼参数/等工具）全部由消费者读活对象与 delta 流推断 —— 用户明确「其他的在干什么由使用者从 delta 流去推断」。
- **中断**：`signal` 管真停、`abortRx` 管别等，**寿命都只到这一圈**。三种会写出"死了得手动复活"的错法见 §5。
- **修复只在进圈开头**（用户提出、比"收尾修"更好）：判据是「要不要回头看别的消息」；消息自己的 `pending→writing→completed/error/aborted` 是状态转移，不算修复。由此崩溃恢复在对外接口上消失。
- **`AgentError` 一个类三个码**（`request-failed` / `stream-failed` / `closed`），**同一个实例**既进 `failed` 事件又挂在 `message.error`；`cause` 用原生 `Error.cause`。曾想给 message 单独定义 `MessageError` 接口，被用户否掉（「统一事件返回的错误对象和 message.error 的形状」）。
- **错误文本绝不进 `content`**；**不重试、不分类、不翻译、不降级**（用户选 a）。厂商错误码不归一。
- **`denied` 与 `failed` 是两个事件**：前者历史里一个字没多（占位还没建），后者留下痕迹。因此 `onInnerLoopStart` 必须排在建 assistant 占位**之前**。
- **工具**：并行、按调用顺序落地、失败即「没给出有效结果」→ 一条 tool 消息回给模型、引擎不停圈。`exec(): Promise<MessageContent>` 接口不变 —— 用户纠正过：所谓"工具流式输出"指的是**模型在流式拼工具参数**，不是工具自己在吐。
- **subagent 是 core 概念**（用户否定了"搬去 SDK"）：core 欠委派动作、血缘、统一事件转发（同一套事件名 + "哪个子 agent"标记）、两个缝；只有"怎么造出来"从注入回调进，形态就是 `AgentToolLazy`，eager 那个删。
- **`source` 一律带**（含宿主注入的隐藏 cwd 消息），判别结构 `{kind:"user"|"agent"|"system", label?}`；**`source` 里不许放 `Agent` 引用**（落库会成环，裁了就变形）。
- **命名口径**：事件说「发生了什么」（`messageAdded` / `toolFinished` / `failed`），钩子说「缝在哪儿」（`onOuterLoopStart` / `onInnerLoopStart` / `onToolEnd`）。同一位置钩子在前（能改）、事件在后（已定）。
- **AgentRegistry 放 host**（`CORE.md` 未收录，属宿主侧结论）：它要判的每件事只有宿主知道；SDK 已有 Scope 管能力。
- **请求体形状与 `ToolCallContext` 形状维持现状**，本轮不重设计（用户明确）。
