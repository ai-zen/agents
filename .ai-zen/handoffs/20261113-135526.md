## 🧠 Key Decisions

- **A1–A13 架构定论**（`architecture.md` §1）：单进程、单监听单 WS、契约归服务端自己、JSON-RPC 2.0 为底（不用批量/强制错误码空间）、所有连接要凭证（本地靠自动填充无感）、`node:sqlite`+worker+WAL、照桌面端三层按需扩展、agent 跑完即弃+Scope 空闲 10 分钟回收、能力清单每个方法一条。
- **R21**：消息内容一律用 core 导出（`AgentNS.Message` / `MessageContent` / `ToolCall` / `Delta` / `Usage`），wire 只包「非消息事实」的薄外壳。
- **R56**：`conversation.create` 不落库（首次 `send` 或首次 `asset.begin` 才落库 + 写一条 hidden 的 cwd 消息）；**R73**：发送前停在「新对话」屏，草稿不进侧栏。
- **R70–R72**：`/model`、`/think` 改**会话级并持久化**（`conversations.modelId` + `thinkingLevel`），全局一律改 agent 定义，换模型必须清档位；内存覆盖那套已删。
- **R74**：保留 `AppConfig.defaultModel` 作三级解析的兜底（会话 > 助手定义 > 全局兜底），三级全空报 `error.modelUnresolved`，绝不静默挑一个。
- **R75**：推送事件一律用 core 原始形状，不许压成字符串或发明平行形状。
- **R76**：`asset.get` 回真实 `width`/`height`（服务端解 PNG/JPEG 头，零依赖，其它 `null`）。
- **素材持久化口径**：库里只存 `__asset_id`（扩展字段，`__` 前缀一律是本地扩展），发送前由 core 的 `formatContent`/`formatContentSection` 白名单剥离（`formatHistory` 递归调用它们，三者都可重写），再按当前模型替换。
- **素材缓存口径（用户三次收紧后）**：同端点命中就用 `file_id`；**换服务商（端点变了）就 base64 内联**，不重传；**失败就报错**——不自动重试、不清缓存、不判失效、不设 TTL、不做重试判据。
- **死路（别再走）**：
  1. 从旧服务端代码 (`bad-src`) 反推需求 —— 已删除，判为垃圾。
  2. 自己发明消息/段/用量类型 —— 用户当场纠偏（R21）。
  3. 用 `asset://` 塞进 `image_url.url` —— 用户改成 `__asset_id` 扩展字段（白名单剥离更干净、前缀缓存无损）。
  4. 为罕见边缘情况写自动重试/失效判定/TTL —— 用户三次要求删掉（「报错就报错」）。
  5. 在事件里把结构化事实压成字符串（`content: string`、`runningTools: string[]`、`notice.text: string`）—— R75 已否。
