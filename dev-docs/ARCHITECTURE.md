# host 实现规范

这个包是一个本地常驻服务：一个 WS 端口、一个 SQLite 文件、若干常驻 agent。

**代码里不许引用本文件**（不写「见 §x」那种坐标）。引用会把规范变成脚注，而脚注会跟着
文档过期。规范要短到能被记住；记不住说明它太长，该删。

---

## 一、一个事实一份形状

同一件事只允许一个类型。派生值当场算，不落库、不搬层。

> 判据：加一个业务字段，要改几处？超过两处就是有第二份。

**这条管的是被持有两份的状态，不是「两个消费者读同一个源头」。** `McpConfig.effective()` 给配置面列「现在能用什么」，SDK 的发现拿同一批文件去连「这些怎么连」—— 源头只有一份，两份输出给的是不同的问题。把它当成重复删掉一个，就是另一种形式的过度归并。

「读不到」只有一种表示：`infra` 层回 `undefined`，由知道实体类型的域决定要不要折成 `not_found`。

## 二、契约声明一次，声明在实现旁边

一个方法的入参与出参写在它自己的 procedure 上。全仓没有第二张方法清单。

> 判据：方法名字符串在源码里出现几次？多于一次就是有第二份。

## 三、形状校验交给 schema，服务层信入参

手写 `typeof` / `Array.isArray` / `Number.isFinite` 一律删。留下的只有世界状态：
`not_found` / `busy` / `unsupported` / `config_invalid`。

不为不可能发生的处境兜底——答不出「哪条路径会走到」的分支就是死代码。

## 四、注释只写「为什么不那么做」

代码能表达的，注释不重复。名字能表达的，注释不解释。

一段注释如果是在解释「桥」「闸」「收口」这类自造词，正确做法是把词换掉，不是加注释。

## 五、分类按域，不按层

`infra/` 加上 `modules/<域>/`。没有 service 层、handler 层、DTO 层、barrel `index.ts`。

- `infra/` 不认识业务：那个目录下不许出现 session / agent / message / workspace / asset。
- 依赖单向：`modules/* → infra/`，反向不成立。
- 只有两个入口同时 import 多个模块：装配根 `app.ts`，以及命令行 `cli.ts`。

## 六、一行一个 JSON

每张表只有 `id` + `payload`。排序、过滤、唯一性要用到的字段，能由库从 `payload` 里算出来的一律写成生成列，JS 从不写它们。

只有**从 `payload` 取不出来**的才做真列，而且每一列要答得出「为什么取不出来」：
`messages.seq`（并发写入的单调量，不是消息身上的东西）、`messages.createdAt`（由宿主在第一次落库那一刻给，core 的 `Message` 上没有这个字段）、`messages.searchText`（FTS 的索引产物）。

## 七、活物有唯一所有者

一个活物一张登记表，在它自己的域里。跨域只传值，不持有。

> 判据：同一件事的登记表出现在两个域 = 有第二份。

## 八、标准问题用标准库

tRPC / Zod / `node:sqlite` / `EventEmitter`。造轮子的门槛是查过现成的，并写清它为什么不行。

## 结构

```
src/
  index.ts    包出口
  app.ts      唯一装配根
  cli.ts      命令行入口（serve / token / version）
  infra/      不懂业务：db、json-table、bus、errors、files、paths、version、hostFile
  modules/
    events.ts         事件判别联合（唯一的业务事件形状）
    i18n/             文案：键是那句中文原文，英文表按它索引
    config/           磁盘上的配置：general · models · agents · mcp · discovery
    workspace/        项目行（cwd）
    scope/            能力容器（活，按目录，无表）
    session/          会话行 + 消息 + 自动命名
    agent/            执行体（活）+ inbox 表 + 一次性执行
    connection/       客户端连接（活：语言、凭证、上传）
    asset/            素材
    credential/       宿主访问令牌
    question/         表单（活，不落库）
    handoff/          交接
    search/           全文检索
    notice/           通知
```

两对「行 / 活物」，都是 1:1 且非对称存在（活物可能不在，反向永远不成立）：

```
workspace/ 行 ──▶ scope/ 活      按目录
session/   行 ──▶ agent/ 活      按 sessionId
```

非对称的后果：**先叫醒再递话是客户端的编排**，不是宿主的兜底。

**没有草稿。** 输入框里的内容是客户端的状态；会话在发送那一刻随消息一起产生，建行与投递是同一个动作。宿主里因此没有「存在但还没落库」的会话，也就没有第二份形状要同步。

## 用例预算

用例只证明「人会做错、且错了没人发现」的事。每域 0~2 条，不设覆盖率门槛。

不写的三类：

- 断言接线（参数有没有递下去）；
- 断言校验会抛错（那是 schema 的活，schema 是声明式的）；
- 断言规则（规则在上面八条里，靠评审，不靠红灯）。

唯一必须有的是跨进程真流程：起宿主、连 WS、发一句话、收到流。

> 判据：一个新域的第 3 条用例出现时，必须说出它证明的是哪个人会犯的错。说不出来就删。
