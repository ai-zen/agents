# 4.8 文案与语言

> 第四部分（新版需求）之八。这一册只讲「一句话由谁渲染、在哪一刻渲染、用哪种语言」。

**语言是用户的属性，不是连接的属性。** 这个项目是单用户：无论从哪个端连上来，都是同一个人。

两边各一份，位置都写死：

- **宿主**：只有一份，挂在宿主应用上（`HostApp`），值来自 `config.general.language`；对外只暴露一个 `t(..)`，调用那一刻现读。没有连接级、没有请求级的状态，也没有按请求实例化的服务。
- **客户端**：自己的那一份就是 `app.lang` 与 `app.t(..)`，与宿主那份无关 —— 宿主发过来的句子已经是成品，客户端不再重渲染。

三条后果：

1. **用户可见的文本在产生处就本地化好**，做法就是在字符串字面量外面直接套一次 `.t(..)`：字面量本身就是键，渲染在那一刻完成，之后一路上都是句子。没有出口渲染这一层，更不做「递归遍历对象把码换成句子」；客户端也不做二次渲染，不维护自己那份文案表。
2. **错误码只用于条件判断**，不用于匹配文案。
3. **宿主自己的错误与日志一律英文**，只记码与结构化细节，不记用户那句——它面向开发者与日志聚合，不是给用户看的。

**通知也是这条规矩**：产生那一刻就把语言定下来，落库存的就是那句成品句子（见 4.5）。

**代价写在明处**：通知落库存的是当时那句成品句子，用户之后改了语言，旧通知保留旧语言。这是「所有用户可见文本只有一个产生点」付出的代价，认这个代价。

## 与旧版的不同

| 事 | 旧版 | 新版 |
|---|---|---|
| 语言存在哪 | 本机偏好文件 | **宿主一份**（挂在宿主应用上，值来自配置）；**客户端一份**（`app.lang` 与 `app.t(..)`）。不挂连接 |
| 句子在哪拼 | 出网前按连接语言拼（存码 + 参数） | **产生处就渲染**：字面量外面套一次 `.t(..)`，之后一路是字符串 |
