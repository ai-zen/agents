# 四、新版需求（六）：观测与文案

## 4.15 观测：不为字段加接口，消息变化要有观测点

**不在客户端与宿主之间为某个字段单开一个接口。** 客户端要的东西只有两种入口：一条事件流，和一次能读回快照的调用；两者合起来必须够它还原出完美的 messages。一旦发现「这个字段得再开一个方法去查」，就是方向错了 —— 那等于把客户端当成一个需要逐字段喂的界面。`[用户]`

**事件加不加、怎么加，是 SDK 的事，需求不管。** 需求只要求它交得出明确的观测点：一条消息出现、变化（包括流式期间正文在长）、定稿、消失，这四件事分得开；订阅者不必轮询，也不必靠比对猜。事件带的是**当时那条消息的完整对象**，不是逐字段的差异。`[用户]`

**优先从内存里读状态、读消息。** 有 agent 就从它的内存读（那才是真身，库里那份可能滞后，也可能压根没有）；没有 agent 了才读库（那时库就是它的全部）。**交接过程不持久化，所以交接期间也照样从内存读** —— 曾经有人给交接开了「改读库」的例外，那是错的。subagent 从不入库，所以也只能从内存读（见 4.6）。`[用户]`

**message 里的错误字段仅用于客户端回显**，跟消息一起按原样持久化；**原始的错误对象走错误事件**。`[用户]`

| | 落在哪 | 活多久 | 谁用 |
|---|---|---|---|
| **消息上的 `error`**（core 的 `AgentError`：码 + 原文；`toJSON()` 就是这两格） | 跟消息一起**原样**落库 | 同消息，重启重连都还在 | 界面把那条消息标红并说清「为什么」 |
| **错误事件**（同一个错误对象的当下推送：码 + 原文 + `detail`） | 走**错误事件** | 只在线时存在 | 日志、排查、要看技术细节的地方 |

两路不互相替代：消息上那一条是**活得比进程长**的最小事实，事件里那一个是**完整**的当下对象；要事后追，看宿主日志（4.9）。

**契约上的错误载荷只有三格**：`code`、`message`、`details`。

- `code` 给客户端做**条件判断**（`busy` 就给重试、`unauthorized` 就提示换凭证），也给日志分类。它不用来匹配文案。
- `message` 是**服务端渲染好的成品句子**，客户端原样显示。
- `details` 只在客户端确实要据此走不同分支时才有。**不为拼句子而存在的字段一律不进协议**——旧的 `{field}` / `{size}` 那批占位符参数全部消失。

## 4.16 语言与文案

**语言是用户的属性，不是连接的属性。** 这个项目是单用户：无论从哪个端连上来，都是同一个人。

两边各一份，位置都写死：

- **宿主**：只有一份，挂在宿主应用上（`HostApp`），值来自 `config.general.language`；对外只暴露一个 `t(..)`，调用那一刻现读。没有连接级、没有请求级的状态，也没有按请求实例化的服务。
- **客户端**：自己的那一份就是 `app.lang` 与 `app.t(..)`，与宿主那份无关 —— 宿主发过来的句子已经是成品，客户端不再重渲染。

三条后果：

1. **用户可见的文本在产生处就本地化好**，做法就是在字符串字面量外面直接套一次 `.t(..)`：字面量本身就是键，渲染在那一刻完成，之后一路上都是句子。没有出口渲染这一层，更不做「递归遍历对象把码换成句子」；客户端也不做二次渲染，不维护自己那份文案表。
2. **错误码只用于条件判断**，不用于匹配文案。
3. **宿主自己的错误与日志一律英文**，只记码与结构化细节，不记用户那句——它面向开发者与日志聚合，不是给用户看的。

旧口径「存码 + 参数、出网前按连接语言重渲染」作废，中间那版「语言挂在连接上、断开即忘」也作废：前者的前提是「一个进程里可能同时存在几种语言」，后者看起来只多一格，实际要让每一个渲染点都去问「这条连接说哪种语言」，还会把「用户改了语言」变成一份快照。同一条口径下：通知落库存的是当时那句成品句子，用户之后改了语言，旧通知保留旧语言；这是「所有用户可见文本只有一个产生点」付出的代价，认这个代价。
