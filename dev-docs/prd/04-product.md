# 四、新版需求（一）：谁在说话、结果从哪来、生死

> 第三部分是存量，这里写**新模型**与**改口**。两部分合起来才是完整规格。
> 每条后面标来源：`[用户]` 用户拍的、`[AI]` AI 拆的（见第二部分，可推翻）、`[旧]` 旧版已有。

## 4.1 三个东西

**一份记忆**：这段会话说过的话，**只有一份**。会话行上的身份（名字、项目、助手、模型、思考深度…）见 1.4。`[AI]`

**这份记忆是个 mutable 数组**：**没在跑的时候可以直接改它**（撤回、编辑、交接换记忆都走这条），**跑起来的时候不许从外面改** —— 那时候要影响它只能投递。`[用户]`

**一个 agent 实例**：每段会话只有一个。它不在的时候，记忆照样在。`[用户]`（下文说"agent"就是它）

**一个 inbox**：别人放进来的话先堆在这儿，agent 按自己节奏取走、变成记忆里的一句话。**inbox 里剩什么，要回显到客户端界面上。** `[用户]`

## 4.2 谁能说话、怎么说

**谁能投**：**inbox 谁都可以投** —— 用户、别的会话的 agent、外部程序、定时器。`[用户]` **过滤、鉴权是业务的事**：现有鉴权（凭证）本来就够，宿主不做额外准入判断，也不区分"人"和"程序"；现在根本没有这方面需求，也别为将来预留。`[用户]`

**任何消息投递都不创建会话、也不复活会话** —— 投到死会话直接报错，跟来源没有任何关系（见 4.4）。`[用户]`

**用户说的话也是一条投递，永远经过 inbox** —— 这是**正常输入**唯一的一条路，不管是谁、不管什么时候。
（注意别把它读成"记忆只读"：记忆是 mutable 的，没在跑的时候能直接改 —— 但那是改记忆，不是"说话"。见 4.1。）

**投递成功不说明会被处理，也不说明会有人回**；**投递失败只回给投递方**。宿主不广播、不记账、不做"通知"：谁的事谁处理，由那个 agent 自己跟用户说。`[用户]`

## 4.3 结果从哪来

**没有"结果"可以领。** 谁想要答案自己看；想要对方回话，等对方自己回 —— 对方回话时，也是往你的 inbox 里放一句，跟你同事发消息一模一样。`[用户]`

**投递与结果这条链上**没有谁在等谁。常驻会话也没有"它什么时候跑完""跑了多久""这次的结论是什么"这类东西 —— 没有"一次运行"这个对象可以被计时、被结算、被回报；要知道它在干什么，自己看（见 4.4 四格与 3.9 的分阶段）。

### 一次性会话：唯一的逃生窗

有一类会话注定只有一条因果链、没有第二个触发方，等它是安全的：

- 同步等结果的**subagent**（它派出去就是为了拿一句话回来）
- CLI 的**纯 stdio 模式**（一次调用、一个答案、一个退出码）
- **独立交接**（摘要那一路，本身就不是任何会话的一次运行）

这些用 `send` / `runOnce` **等到空闲为止**再返回。边界很清楚：**能等，是因为没有别人会同时往里塞东西**。常驻会话永远不满足这个条件（它可以被任意触发方从闲推到忙），所以那里没有 `send`。`[用户]`

它们**不是"一段会话的第一次运行"**，也不是段/轮/圈里的一个 —— 它们就是一次到头的会话，跑完就散。`[用户]`

> **两个口子，一个包一个**：`send()` 是「投递 + 等到空闲、**不关门**」本身；`runOnce()` 就是它在外面套一层收尾（跑完就关）。两者都只给一次性会话 —— 常驻会话那边只有 `push()`。`[用户]`

## 4.4 生死

- **不自动生**：**任何消息投递都不创建会话、也不复活会话** —— 投到死会话直接报错，跟来源没有任何关系。`[用户]`
- **不自动死**：没有空闲回收、没有引用计数。`[用户]`
- **将来会有定时器**，但定时器只做一件事：**往 inbox 投递**。它能吵醒一个本来就活着的会话（闲不闲无所谓），**不能造一个、也不能复活一个**。`[用户]`
- 会让它死的只有三件：**用户按杀死**、**用户删掉这段会话**、**进程退出**（那不是回收，是机器没了）。`[用户]`
- 删掉这段会话是**硬删**，删前警告并把代价说清；删会话按「会话 ↔ 素材」关系清引用，**没有引用了才删素材**（见 4.11）。`[用户]`

**能把一段会话跑起来的只有三条路**：人运行它；agent 用明确的工具派生 / 激活会话；客户端点发送时先判这段是死是活，死的就调接口复活、再投递。`[用户]` **谁能给谁投、能复活谁，宿主不做任何限制** —— 靠 agent 自己的知识与记忆（同 4.6）。`[用户]`

**为什么不能谁都唤醒**：会烧钱、会在用户不在场时往记忆里写东西、会让已经结束的会话自己动起来；而且谁都能唤醒等于任何一段会话都能被永久养活着。内存在此是唯一代价 —— 它可见、可杀，所以可接受。`[用户]`

### 状态是四件事，不是四格

| 维 | 是什么 | 取值 |
|---|---|---|
| **闲 / 忙** | 只读的观测值：agent 此刻在不在活动 | 闲 / 忙 |
| **输入闸** | 外面的话收不收 | 开 / 关 |
| **输出闸** | agent 取不取 inbox 里的东西 | 开 / 关 |
| **死活** | 有没有 agent 实例 | 活 / 死 |

**这四件事用户都要看得见**：这段是闲还是忙、两个闸各是开还是关、它是不是还活着。`[用户]` **「闲」与「输出闸关」必须分得开** —— 一个是手上没活，一个是不取新活。

**「暂停 / 继续」按的是输出闸**：暂停＝关输出闸（收话、不动），继续＝开输出闸（压着的按原顺序接着跑）。**「中断」是另一件事**：掐掉在途的请求与工具，并把输出闸关上 —— 所以中断完落在「输出闸关」，还能继续。

> 旧的「死 / 忙 / 闲 / 暂停」四格表**作废**：暂停不是与闲忙并列的一格，它是输出闸那一维；「死」也不是其中一格，而是有没有 agent 实例。

### 暂停与中断是两件事，中断不是杀死

**暂停只是关输出闸**：手上这批已经取在手上的照常跑完，从下一批起不再取；它不打断任何正在跑的东西。**中断**是掐掉在途的请求与工具，并把输出闸关上。

**界面上的按钮**：原则上四个 —— 暂停 / 继续 / 中断 / 发送，其中暂停与继续是同一个按钮点击后互切。**实践中输入框里只放两个**：一个「继续 ⇄ 中断」互切，一个「发送」；**不向用户提供优雅暂停这个按钮**（要停就是中断）。`[用户]` 交接期间界面只留中断，别的都不给。

**中断不是杀死 —— 这两件事没有关系。** 「马上停」有两个动作，一个是停一下，一个是收掉：

| | **中断（`abort`）** | **杀死（`kill`）** |
|---|---|---|
| 之后 | 输出闸关着，还能「继续」 | 没有 agent 了，只剩「发话」能叫起来 |
| 在途的请求 | 掐断 | 掐断 |
| 没消费的条目 | **留着** | **作废**（库里也删） |
| 输出闸 | 关着（就是它关的） | 没了 —— 人都没了，谈不上闸 |
| 记忆 | 照旧在 | 照旧在 |

所以实现里**绝不能**让"中断"顺手把 agent 收掉 —— 那是把两个动作混成一个，用户按的是"停一下"，不是"收掉"。

（一次性会话是例外里的一格：它本来就只有一条命，掐断等于到头，没有"继续"可言 —— 但那是它的性质，不是把 abort 当 kill 用的理由。）

### 换模型不是死

**换模型 / 改配置不必然换掉 agent**：要不要重建只跟「改的是不是构造参数」有关；插件完全可以把参数挂在 agent 上，刷新就是给字段赋值，根本没必要杀 agent（见 4.7）。真要换掉 agent，会话 id 与 11 格照旧不动、别人送来的话一句不丢；**换掉之后暂停要不要保留，未定**。`[AI]`

**交接的收口不是死**：原地交接，换完之后这段会话还活着（见 4.5）。
