# 4.7 观测与错误

> 第四部分（新版需求）之七。这一册只讲两件事：客户端该从哪儿看见事实，以及错误走哪两路。
> 事件怎么设计（哪几条、什么时候发）是 SDK 的事；这个包里的具体切点在 TRD 的「运行时活物」那一册。

## 不为字段加接口，消息变化要有观测点

**不在客户端与宿主之间为某个字段单开一个接口。** 客户端要的东西只有两种入口：一条事件流，和一次能读回快照的调用；两者合起来必须够它还原出完美的 messages。一旦发现「这个字段得再开一个方法去查」，就是方向错了 —— 那等于把客户端当成一个需要逐字段喂的界面。`[用户]`

**事件加不加、怎么加，是 SDK 的事，需求不管。** 需求只要求它交得出明确的观测点：一条消息出现、变化（包括流式期间正文在长）、定稿、消失，这四件事分得开；订阅者不必轮询，也不必靠比对猜。事件带的是**当时那条消息的完整对象**，不是逐字段的差异。`[用户]`

**优先从内存里读状态、读消息。** 有 agent 就从它的内存读（那才是真身，库里那份可能滞后，也可能压根没有）；没有 agent 了才读库（那时库就是它的全部）。**交接过程不持久化，所以交接期间也照样从内存读** —— 曾经有人给交接开了「改读库」的例外，那是错的。subagent 从不入库，所以也只能从内存读（见 4.3）。`[用户]`

## 错误两路

**message 里的错误字段仅用于客户端回显**，跟消息一起按原样持久化；**原始的错误对象走错误事件**。`[用户]`

| | 落在哪 | 活多久 | 谁用 |
|---|---|---|---|
| **消息上的 `error`**（core 的 `AgentError`：码 + 原文；`toJSON()` 就是这两格） | 跟消息一起**原样**落库 | 同消息，重启重连都还在 | 界面把那条消息标红并说清「为什么」 |
| **错误事件**（同一个错误对象的当下推送：码 + 原文 + `detail`） | 走**错误事件** | 只在线时存在 | 日志、排查、要看技术细节的地方 |

两路不互相替代：消息上那一条是**活得比进程长**的最小事实，事件里那一个是**完整**的当下对象；要事后追，看宿主日志。

**契约上的错误载荷只有三格**：`code`、`message`、`details`。

- `code` 给客户端做**条件判断**（`busy` 就给重试、`unauthorized` 就提示换凭证），也给日志分类。它不用来匹配文案。
- `message` 是**服务端渲染好的成品句子**，客户端原样显示。
- `details` 只在客户端确实要据此走不同分支时才有。**不为拼句子而存在的字段一律不进协议**——旧的 `{field}` / `{size}` 那批占位符参数全部消失。

## 与旧版的不同

| 事 | 旧版 | 新版 |
|---|---|---|
| 错误怎么到客户端 | 一个码 + 参数，出网前按连接语言拼句子 | **两路**：消息上那条只作回显、跟着消息原样落库；完整对象走错误事件。**句子在产生处就渲染好** |
| 事件里带什么 | 字段级推送 | 带**当时那条消息的完整对象**，客户端据此还原出完美的 messages |
