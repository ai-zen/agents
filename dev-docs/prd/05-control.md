# 4.2 控制一段会话

> 第四部分（新版需求）之二。这一册只讲「一段会话能被改什么、改了要不要重建」。
> 会话的组成与生死在 [4.1 会话与记忆](04-session.md)；配置面本身（端点、模型、助手、默认项）是存量需求，在旧版需求那一册。

## 有上游默认、会话可覆盖（四样）

| 改什么 | 默认来自 | 要不要重建 agent | 确认 |
|---|---|---|---|
| 模型 | 助手定义 | **要** | 它忙时二次确认；闲/暂停直接换 |
| 思考深度 | 模型 | **要** | 同上。**换模型时它被清空** |
| 交接阈值 | 模型 | 不用 | 不问 |
| 防护阈值 | 模型 | 不用 | 不问 |

**判据只有一条：改的是不是 agent 的构造参数。** 是就得重建，不是就不用；名字、开关、两条阈值它根本不读，改了当场生效。`[用户]` **但"要重建"不等于"必得杀 agent"**：插件完全可以把参数挂在 agent 上，刷新就是给字段赋值，根本没必要杀 agent —— "怎么安全地更新到 agent 上"是要论证的工程问题，不是"换掉"一句话。`[AI]`

## 本来就在会话上的字段（不存在覆盖谁）

| 改什么 | 要不要重建 agent |
|---|---|
| 名字 | 不用 |
| 自动交接开关 | 不用 |

**全局改**（改助手定义，影响所有用它的会话）：要一次二次确认，把代价说清（正在写的内容会断）。`[用户]` 要不要真的把活着的 agent 全重建，**也不一定** —— 同上，看能不能就地刷新。`[AI]`

**换模型不是杀死**：改配置引起的重建，用户按的是"换模型"，不是"杀死" —— **inbox 里的东西一句不丢**（会话 id 与 11 格都没动）。`[用户]`

**重建之后暂停保留**：重建前输出闸是关的，重建后还是关的。闸是用户的决定，不属于执行体，换一个执行体不该把它改掉。`[用户]` 交接那条不同：交接完成即开闸（见 4.4），因为交接本身就是换人接着干活。

## 两条线的口径

量的都是**请求前的输入用量（绝对值）**，不是"记忆多长"、不是百分比：

| | 交接阈值（软线） | 安全防护阈值（硬线） |
|---|---|---|
| 到了怎么办 | 触发交接 —— 原地交接，接着往下走 | **这次请求不发，中断** |
| 关系 | **建议**硬线 ≈ 软线 × 1.5；两个数各自可设，不是硬绑 |

- **交接那一次请求也不让路**：硬线照旧拦，要避免撞线就把阈值配得够宽，靠配置留出余量。`[用户]`
- **撞上硬线 = 直接报错**，不是把请求发出去让厂商回错，也不是警告后放行，**不做任何兜底**。`[旧] + [用户]` 所以"用户拒绝交接后继续聊"要读成：聊到撞硬线为止；撞了之后要么交接、要么换模型、要么新开一段。
- **除了这两条用量线，别的上限一个都不设** —— 不设"最多跑多久"、不设"最多调几次工具"。`[旧]`
- **这道线罩住所有层级**；被拦下的那一层是**软停**（那个死掉，用户的会话继续）。`[旧]`

## 与旧版的不同

| 事 | 旧版 | 新版 |
|---|---|---|
| 改配置怎么生效 | 关闭配置中心后**重建会话** | **就地刷新**：已有的项目重新发现（MCP 按定义对账、断掉不需要的连接），消息与上下文保留。**理论上不杀任何会话，下一次请求就生效** —— "怎么安全地更新到 agent 上"是待论证的工程问题，不是"换掉/invalidate"一句话 |
| 交接那次请求要不要越过硬线 | 硬线让路（谁设的限谁让路） | **不让路**：硬线照旧拦，把阈值配宽点（见上「两条线的口径」） |
| 配置 JSON 写坏了怎么修 | 报错等人修 | **直接恢复成出厂配置**并写回，说清哪个文件坏了（本机、项目侧、`~/.agents` 各层一视同仁）；**不去猜怎么坏的、不做精确修复** |
