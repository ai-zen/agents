## 🧠 Key Decisions

- **判据先行**：模型不是攻击者；工具层不承担安全边界（`rm` 只是 `fs.rm` 薄封装，等价能力由 `exec` 提供）；工具返回错误文本是合法行为；只修"正常用法会踩到"的问题。—— 因此撤销了路径穿越、`rm ""` 护栏、SSRF、任意写 RCE、`call_skill_sub_agent` 继承父工具等 14 条。
- **`lastUsage` 应当消失**：用户指出"messages 里已有真实用量"，代码证实 core 在 `Agent.ts:431-433` 同时写 `this.lastUsage` 与 `receiver.usage`，是同一事实的两份拷贝。最终：删字段 → 只读派生 getter，禁写；交接回合的放宽由**护栏自己**判断（`isSuspended`），"谁做限制谁放宽"，绝不去动用量字段。
- **`send()` 的返回值问题归 core**：core 自己的注释写明 `onAfterSend` 可做迁移，却在钩子前抓快照；`run()` 唯一出口就是 `return this.messages`，故改 1 行即可，SDK 侧无需兜。
- **并行 `edit` 不修**：实测写前校验（读前/写前 `stat` 比对）对同进程并发只能拦 1/20，只有串行化有效，但提示词已覆盖 → 不值得。
- **`download_file` 的 abort 清理分支直接删**：当前设计下 abort 只可能发生在唯一那次 `writeFile` 之前，磁盘文件要么原封不动要么已写完，不存在"半成品"，该分支唯一作用是删别人的文件。
- **`batch_edit` 保持级联**（用户裁定）：只修失败原因文案与 `replacedCount` 口径。
- **走错的路（勿重复）**：① 曾建议在 SDK 侧给 `migrate()` 加"原地改数组"绕开 `send()` 问题 → 被否，正确做法是改 core 返回值；② 曾把 ReDoS/路径穿越/SSRF 定为 P0 → 全撤；③ 曾据"CLI 未实现"推断无人清 `lastUsage` → 错，真 CLI 在 `/home/ubuntu/projects/ai-zen/cli`，它会清，只是用了写字段的方式。
