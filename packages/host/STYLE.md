# host 代码风格

核心宗旨只有一条：**可读性**。下面每一条都是它的推论，冲突时按宗旨裁决。

代码里不引用本文件。

---

## 一、名词

用业界已有的词。**不造词**。

> 判据：这个词在 MDN / RFC / 一个成熟库的文档里能不能查到同义用法。查不到，或者需要先解释一遍才懂，就不是共识。

产品自己的概念（会话、项目、素材、交接、提问）必然存在，它们走另一条路：

- 在散文里首次出现时用 `[术语]` 标记；
- `GLOSSARY.md` 里必须有条目；
- **一个概念只有一个名字**，禁同义词。

`[术语]` 只用在散文（注释、文档、提交信息）里。标识符直接用那个词的英文，不需要标记。

## 二、散文

文字部分是给人读的正式文本，不是写给自己看的便签。

- **不用刻意省字的口语去表达本来需要完整表述的事。** 写“中止进行中的请求”，不写“掐在途”；写“是否存在”，不写“在不在”。
  > 判据：这句话离开上下文还成立吗？主语、动作、对象都在吗？能不能翻成一句结构完整的英文？
  > （与缩写无关：`cfg`、`t`、`doesn't` 都不受这条约束。）
- **不用口语、拟人、比喻。** 消息不叫“话”，不写“顺手”“烧 token”。
- **不用加粗强调。** 需要强调说明句子没写清，回去改句子。
- **一句话一个语境**：要么说行为，要么说依据，不混。
- 标识符在散文里用反引号照抄原样，不改写。
- 人称用第三人称陈述句，不用“你 / 我们”。

## 三、注释

**0 行是合法结果。** 注释密度不是指标，是诊断信号——它高的时候，问题通常在旁边那段代码的结构里。

只写两种：

1. **不明显的陷阱与前提**——读者会想错的地方（SQL 的 NULL 语义、分词器的最小长度、两步之间不能换的顺序）。
2. **为什么不那么做**——防止后人顺手“简化”。

两种的共同点：**代码里看不出来，而读者多半会想错。**

不写：

- 复述代码本身；
- 分节符（`// ---- 投递 ----`）——它是结构缺失的代偿，该做的是拆文件；
- 加粗标语；
- 文档坐标（`见 PLAN §5`）——坐标会过期，过期注释比没有更糟；
- 注释引用注释。

> 判据一：删掉这一行，读者会不会做错一个决定？
> 判据二：这段解释能不能被代码替代（改名 / 改结构 / 加类型）？能，就改代码。

## 四、代码构成

- **单根 `HostApp`**：一个构造点，没有模块级单例，没有隐式全局。构造顺序即依赖顺序，写在同一个地方。
- **依赖单向**，向下。循环依赖只靠事件解，不许用可选注入绕。
- **可以传根**，前提是接收方用 `Deps` 声明所需：

  ```ts
  interface AgentDeps { readonly config: ConfigModule; readonly session: SessionModule; readonly t: Translator }
  new AgentModule(this)   // 结构类型保证根上真有所需的那几个
  ```

  `Deps` 里不许出现根类型；不许把 `deps` 断言回根；**不许有可选成员**——要就给，不要就把那块功能删掉。
- **只持有两种东西**：生命周期与进程一致的对象，以及登记表。会被整体替换的单个实例（`Scope`、`agent`、连接）一律现取：

  > 判据：这个字段存的东西会不会整个换掉？会，就别存。换掉之后谁还指着旧的？答得出名字，就是写错了。

- **传对象，不传字段；传闭包，不传值；构造参数保持整体，不在签名里解构。**
- **类内成员按固定顺序**：静态常量 → 实例字段 → 构造函数 → 公开方法 → 私有方法。
- **无状态的纯函数留在同域的文件里做模块级函数**，不当类的成员。判据：用到 `this` 吗？用不到就不是方法。

## 五、函数拆分

**只有一个调用点的函数默认内联。**

三种例外：名字本身承载了调用处要读的信息；语法要求边界（回调、`try`、递归、生成器）；跨文件。

> 边界不自然的信号：提取出来的函数要的参数，是原函数局部变量的大半。参数越多，边界越假。
> 读代码的成本是**跳转次数**，不是行数。

## 六、文本产出

文本分三类，各有各的规矩：

| 类 | 谁读 | 写什么 |
|---|---|---|
| 用户可见的文案 | 用户 | 服务端按当前语言渲染好的一句成品 |
| 宿主自己的错误与日志 | 开发者、日志聚合 | 英文 |
| 命令行输出 | 运维 | 英文 |

**文案在产生处本地化**：字符串字面量外面包一次 `this.t(...)`，之后一路是 `string`。不做出口渲染，更不做“递归遍历对象把码换成句子”那一层。

```ts
type Translator = (text: string, params?: Record<string, string | number>) => string;

throw new HostError("not_found", t("找不到 id 为 {sessionId} 的会话", { sessionId }));
```

- **键就是那句中文原文**，不另维护键清单（多一份清单就多一份会对不上的账）。缺译文时回落成原文，并在日志里记一条 `i18n.missing`，不抛。
- 语言在调用那一刻从 `config.general.language` 现读；`t` 是闭包，不是字段。

## 七、失败

**跨 wire 的失败**（会回给客户端）→ `HostError(code, message, details?)`：

- `code` 给客户端做条件判断、给日志分类，不用于匹配文案；
- `message` 是按当前语言渲染好的成品句子；
- `details` 只在客户端确实要据此分支时才有，**不为拼句子存在的字段不进协议**。

**宿主自己的运行事故**（启动、文件、磁盘）→ 英文 `Error` + `cause`，只进日志。这类失败不跨 wire，硬包成 `HostError` 只能丢句子或安错码。

日志不记用户那句，只记 `code` + `details`。

英文文本的措辞：

- 完整句，`Cannot` / `does not`，不用缩写形式；大写开头，句末不加句号；
- 结构固定为 `<事实>: <上下文>`，先说发生了什么，再给判断所需的细节；
- 不写零信息量的词（`failed`、`error`、`boom`、`down`）；
- 不拟人、不比喻、不用感叹号、不写 `please`；
- 值用双引号，路径原样；保留 `cause`，不吞原始错误；
- 宿主自己抛的错：跨 wire 的一律是 `HostError`，不跨 wire 的一律是英文 `Error` + `cause`。裸 `Error` 只可能来自运行时或第三方，捕获时要么转换、要么带上 `cause` 往上抛。
