# 架构

这一页讲「为什么这么切」。每一层里有哪些动作、哪些类，留给 [Core API](core.md) 与 [SDK](sdk.md)；宿主这台进程怎么存在，留给[部署](deploy.md)。

## 四层各负责什么

| 层 | 包 | 负责 | 严格没有 |
|---|---|---|---|
| 内核 | `@ai-zen/agents-core` | 一个 agent 的全部行为：外循环取走 InboxEntry、内循环发请求与跑工具、state 的两格、isInputPaused 与 isOutputPaused 连同它们的方法、寿命、事件总线、插件挂载 | 会话与项目、库与任何持久化、网络与凭证、语言与文案、配置文件的读、能力发现 |
| 能力面与运行时 | `@ai-zen/agents-sdk` | 能力面：按目录一份的 Scope，装工具、技能、SubAgent、MCP 服务器与 PeerSession 那三个工具，模型的三级解析，交接。运行时：唤醒 Agent、登记谁活着、给另一段会话 post()、按目录拆容器 | 库、连接、凭证、语言与用户可见文案、会话行 —— 会话对它只是一个不透明的身份 |
| 宿主 | `@ai-zen/agents-host` | 库与表、连接与凭证、客户端杂项（通知、Asset、提问、搜索）、用户可见文案与语言、单实例与发现文件、命令行 | 装 Agent、记谁活着、决定 Scope 什么时候拆、判配置合不合法、算 MCP 合并、管连接与重连 |
| 连接层 | `@ai-zen/agents-client` | 拉起一台宿主、发现（发现文件与凭证交付文件）、凭证来源、重连 | 发版（`private: true`）；被 `core` 与 `sdk` import |

另外三个包不在这四层里，各自只为一件事存在：`@ai-zen/agents-logger`（一个进程一个日志文件，零依赖，只由装配根创建）、`@ai-zen/agents-testing`（几个包共用的测试件，不进生产依赖图）、`@ai-zen/fake-llm`（OpenAI 兼容的假端点）。

## 分层的四条判据

1. 这段代码里出现「谁是活的」「谁认识谁」「什么时候装、什么时候拆」→ 该在运行时（sdk），不在宿主。
2. 这段代码是为了「另一个 agent 也要看到」而在宿主里转了一道 → 该在运行时。
3. 出现 `as unknown as`、或者「造一个假实例满足 sdk 的接口」→ 缺一个端口；端口该由 sdk 定义、宿主实现。
4. 反过来：这段代码只在「读写文件、写库、转事件、校验凭证、渲染文案」→ 它就该在宿主，别往 sdk 搬。

这四条落地成一个可执行的检验：把宿主删掉，只用内核与 sdk 也要能组装出事件驱动、常驻、能互相通信的 agent。做不到就说明分层错了，先改分层，不许用宿主去补。

## 事实从下往上冒，材料从上往下给

| 切面 | 内核 | sdk | 宿主 |
|---|---|---|---|
| 创造 | `new Agent`（历史作为入参） | `createAgent` 加运行时的 `wake` | 无 —— 它只发新身份 |
| 观测 | `on()` 发事实 | 运行时转出，并让别的 agent 也能订阅 | 订阅 → 写库 → 推线上 |
| 持久化 | 不发，只发事实 | 同内核：只发事实 | 唯一的写库口；恢复材料由它交给 `wake` |
| 通信 | `send()` 进 inbox | `post()` 给另一段会话 | 把客户端来的那一条转进去，不解释 |
| 两个开关 | `pauseInput()` / `pauseOutput()` 与两条现读 | 透传 | 转成 procedure 与线上事件 |
| 寿命 | `start` / `stop` / `kill` | `wake` / 收回 | 转成 procedure |

三层守同一条规矩：事实从下往上冒，材料从上往下给；中间没有第二处持有同样的东西。

方向一反过来就出问题：宿主替下层记着「谁活着」，等于在运行时之外多一份会漂移的真相；下层自己去读库，等于把「库是恢复材料」变成「库是事实」。

## 活物：四问与五条判据

生命周期与进程或某个实体绑定的对象没有表。今天就是两个：`Agent` 与 `Scope`。

每造一个活物，四问要先答得全，答不全就先别写代码：

| 问 | 要答的内容 |
|---|---|
| 创造 | 谁造它、造完谁持有、什么时候对外可见 |
| 观测 | 一次性读得回来的那份快照是什么；变化通过哪几条事件说出去；订阅者靠什么判出重复与缺口 |
| 持久化 | 它的哪一部分要落库、落库的切点在哪、恢复时拿什么把它装回来 |
| 销毁 | 谁拆它、拆之前的顺序是什么、拆完库里留什么 |

五条判据：

1. 创造必报事件，且事件先于对外可见。造好 → 报出现 → 快照读口才看得见它。反过来的话，订阅者会先读到一份它还不认识的活物。
2. 快照必须覆盖事件。凡是事件里能表达的状态，打开或列出时必须一次给得全；做不到，事件丢一条界面上就缺一块，而且没人发现。
3. 持久化只有切点，没有自选动作。活物不认识库：它发事实，第三方订阅、冲刷、恢复。要落库的东西必须有一条对应的事件，能落库的东西必须有一个装回去的口；写了却没有恢复口，那份数据只是包袱。
4. 收尾必须成序：报最后一批事实 → 报「我要没了」 → 解订阅 → 作废。之后这个活物不再发出任何事件；先解订阅再报，订阅者永远不知道自己漏了什么。
5. 内存是真相，库是恢复。有活物时读它的内存，没有活物时才读库 —— 那时库就是它的全部。读库只发生在恢复那一刻，写库只发生在事件那一刻。

不套这套的有四个：库里有表的行（SessionRecord、消息、NoticeRecord、AssetRecord）、一次性过程（交接）、连接、提问。它们没有「内存是真相、库只是恢复材料」这一对，各有各的事实。

加一个字段的判据是四处一起改：事件、快照、落库、恢复。改不到四处，说明这个字段有两份形状。

## 事件四件套

每条事件四件固定的事：

- `type`：发生了什么；
- `seq`：这个活物自己的一条单调序号，从 1 开始 —— 订阅者靠它判重复与缺口，也靠它答「从哪接着写」；
- `at`：时刻；
- 载荷：当时那个活物的完整一份，不是差异；归属（哪个活物、哪一层委派、哪次工具调用）一并带上。

事实分三类，持久化的落点不同：

| 类 | 例 | 谁来持久化 |
|---|---|---|
| 发生了 | 新消息、新 InboxEntry | 第一次出现时写一行 |
| 变了 | 正文增量、结构性变化、状态翻转 | 订阅者决定写多细，节流窗口是它的策略 |
| 定稿了 | 一条消息的这一版是终版、一趟请求结束 | 必写，此后这条只读 |

没有「定稿」这一类，订阅者只剩两种坏选择：每片写整行，或者只在收尾写一次、然后在进程死掉时丢正文。

## 持久化只有一个写库口

写库这一件事只在宿主那一侧：内核与 SDK 的能力面只发事实，一个字都不写；宿主订阅这些事实，在自己的切点上写库，再把同一批事实转成线上的事件推给客户端。落库失败不许把推送也拖住。

恢复是反方向的一次交材料：宿主从库里读出历史与上次没被取走的 InboxEntry，装成 `WakeMaterials` 交给 `wake`，别的都不带。所以「关掉再打开，记忆与排队区都在」是这一个口的结果，不是两处各自保存的结果。

## 观察是旁路

订阅者抛错被隔离，转成它自己的 `observerFailed`，不打断被观察的对象 —— 磁盘满不能把推理一起打死。

拦截用钩子，观察用订阅。能拒的钩子（决定「要不要开始干」的那四个钩子）fail-closed、返回判决；其余一律 fail-open、不返回值、不参与任何判断。两者不许共用一个口：一个坏掉的守卫放行了，等于没有守卫；一个订阅者抛了错，不该改变被观察的事实。

策略不进下层：写多细、多久冲刷一次、事务怎么开，都是订阅者的事；活物只提供切点与事实。
