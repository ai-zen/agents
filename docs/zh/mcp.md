# MCP

MCP（Model Context Protocol）这一侧全在 `@ai-zen/agents-sdk` 的 `scope/plugins/mcp/` 里，一共四样东西：把五层配置文件合并成一份清单的发现、管连接与断开的 `McpConnectionManager`、把服务器摊成五个工具的那一层，以及每台服务器上的任务会话。

这一页写给配 MCP 服务器的人：配置在哪儿、怎么写、改完什么时候生效、模型手上那五个工具各要什么参数、任务是什么形状。

## 怎么用

接一台服务器是三件事：写一条配置、让它被发现、让模型去用。

写配置只有两份文件能由界面改：用户级写在 `<数据根>/mcp.json`（缺省 `~/.ai-zen/mcp.json`），项目级写在 `<项目>/.ai-zen/mcp.json`。另外三层是别人的文件，以文件为准（见下一节）。一条配置长这样：

```json
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "..." },
      "description": "GitHub 仓库与 Issue 操作"
    },
    "postgres": {
      "type": "http",
      "url": "https://mcp.example.com/mcp",
      "headers": { "Authorization": "Bearer ..." },
      "description": "PostgreSQL 数据访问"
    }
  }
}
```

让它被发现：`Scope` 启动时、以及 `scope.reload` 被调到的时候，每份已经造好的容器重读一遍配置（宿主那一侧的入口是 `/reload` 与运行时的 `refreshAll()`）。新增的服务器不会主动连 —— 没人调用就不起进程、不建链。

让模型去用：它手上是 `load_mcp`（连上、拿回清单）与 `call_mcp_tool`（调一个工具）两条，读资源与任务另有三个（见[五个按需加载工具](#五个按需加载工具)）。`description` 也在这时候起作用：它进 `load_mcp` 的参数说明，模型据此判断值不值得连。

改完配置什么时候生效、停用会断开什么、超时缺省是多久，见[启用与停用](#启用与停用)。

## 五层配置文件

一份清单来自五个文件，近的在前，同名以更近的为准。

| 层 | 文件 | 谁能写 |
|---|---|---|
| 项目根 | `<项目>/.mcp.json` | 以文件为准 —— 这一份与别的工具共用 |
| 项目 | `<项目>/.ai-zen/mcp.json` | 能由界面改 |
| 项目 | `<项目>/.agents/mcp.json` | 以文件为准 |
| 用户 | `<数据根>/mcp.json`（缺省 `~/.ai-zen/mcp.json`） | 能由界面改 |
| 用户 | `~/.agents/mcp.json` | 以文件为准 |

这五层的次序在代码里就是这五个名字：`workspace`、`workspaceAiZen`、`workspaceAgents`、`user`、`userAgents`。

只有项目那一份 `.ai-zen` 与用户数据根那一份由宿主写，另外三层要么在别人的仓库里、要么在别的工具的目录里：替人写那种文件，等于替人改他仓库里的内容。写回的时候改的是文件原样，只动被点名的那一条 —— 这一版不认识的键、别的工具写进去的键，一个都留着；删一条时这一层里没有它就报 `not_found`，因为它来自更远的一层，删这一层什么也删不掉。

合并的规矩只有四条：

- 同名以更近的那一层为准，更远的那一条连读都不读。
- 近处的一条 `disabled: true` 也算对这一层发过言：它取消了远处同名的定义，而不是「这一层没提过它」。
- 不是对象的那一条连名字都不占。
- 读不出 JSON 的文件记一行日志，然后当它空着 —— 那几台服务器会安静地从清单里少掉，那一行日志是唯一能说原因的地方。

## 三种传输

| 传输 | 字段 | 是什么 |
|---|---|---|
| `stdio` | `command`、`args`、`env` | 起一个子进程，走 stdin / stdout |
| `http` | `url`、`headers` | Streamable HTTP：POST 发消息，可选 SSE 流回来 |
| `sse` | `url`、`headers` | 旧的 HTTP + SSE：GET 建一条 SSE 流，POST 发消息 |

传输方式可以显式写 `type`，也认 `transport` 与 `transportType` 两个别名；三个都没写时按字段推断：有 `command` 就是 `stdio`，有 `url` 就是 `http`。写回文件时只写标准那一个键 `type` —— 一份文件里同时留着 `type` 与 `transport` 之后，人改哪一个都可能不生效。

两件容易踩的事：

- `args` 是一个字符串数组，每个元素就是一个参数，不经过 shell（子进程是 `shell: false` 起的）。所以 `args` 里写 `"--flag value"` 是把一个带空格的参数原样传下去，不是两个参数；要两个就写两个元素。要跑一段 shell 语法，就自己写成 `["-c", "..."]` 之类。
- 子进程的环境变量默认只有一小批（`HOME`、`LOGNAME`、`PATH`、`SHELL`、`TERM`、`USER`，Windows 上是另一批），配置里的 `env` 叠在上面，同名覆盖。把令牌放在 `env` 里，别指望它在父进程的环境里就已经在了。

## 启用与停用

停用只有一个开关：那一条上的 `disabled: true`。没有第二个地方记「这台服务器现在关着」。

停用之后发生什么，取决于 `Scope` 有没有收到那次变更。宿主把配置的变动告诉运行时，运行时让每份已经造好的容器重读一遍配置，容器再让 MCP 插件重新发现一次并按定义对账：

| 这次发现里 | 连接怎么办 |
|---|---|
| 消失了（删了，或被 `disabled: true` 取消） | 断开，缓存的状态与清单一起失效 |
| 定义变了 | 断开；下一次调用按新定义懒连 |
| 是新增的 | 不主动连 —— 没人调用就不起进程、不建链 |
| 一个字节都没变 | 不碰，连接与清单原样留着 |

「定义」算的是连接事实：传输方式与它的参数（`command` / `args` / `env` / `url` / `headers` / `oauth`）。`description` 不进这份指纹 —— 它只影响 `load_mcp` 给模型看的那段文字，改它不该把一条好连接断掉。

所以「停用即断连」是容器收到变更之后的后果，不是界面上按一下就直接断；而「重新启用」也不等于立刻起进程：连接是懒的，下一次模型点这台服务器时才按新定义连上。

连接自己的几条：建连超时缺省 60 秒，超时即断开并抛错，免得一个配错的地址让工具永久挂着；空闲超时 stdio 是 30 分钟，http 与 sse 是 5 分钟，每次调用都续一次；传输断掉时这台服务器被标成已断开并记一行日志，不会自己去重连 —— 重连发生在下一次要用它的时候，过期的清单不会被当作当前那份出示。状态是四格：`disconnected`、`connecting`、`connected`、`error`。

## `description` 给模型看

`description` 不是注释。它进 `load_mcp` 的参数说明：每一台允许的服务器占一行，写成 `id: 描述`，没写描述的就是一句「没有描述」。模型据此知道这一台是干什么的、值不值得连 —— 没有这段文字，模型只能从名字猜。

它也是唯一不影响连接的定义字段：改描述不会断开任何连接，下一次装配时新的描述就带上了。

## OAuth：字段留着，还没有实现

`oauth` 认得这个形状：`{ authorizationUrl, tokenUrl, clientId, clientSecret?, scope? }`，只对 http 有意义。发现那一层把它原样带进 `McpServerDefinition`，连接那一层根本不看它。

所以：字段留着，配了也连不上，别假装支持。需要一个带授权的服务器，今天只能自己把令牌放进 `headers`。

## 五个按需加载工具

MCP 的工具不预先注册 —— 一台服务器有几个工具，要连上才知道。模型手上因此是五个工具，按需加载：

| 工具 | 参数 | 干什么 |
|---|---|---|
| `load_mcp` | `server`（枚举就是允许的那几台）、`include_manifest`（缺省 `true`） | 连上这台服务器，交回它的清单 `{ tools, resources }`；`include_manifest: false` 时只建连接并回一份摘要 `{ server, connected, tools: 数量, resources: 数量 }`，适用于清单已经在上下文里的情形；已经连着的就续一次期再交回同一份清单 |
| `call_mcp_tool` | `server`、`tool`、`arguments` | 调一台已连接服务器上的工具；没连上就回一句「先用 `load_mcp` 连」 |
| `read_mcp_resource` | `server`、`uri` | 读一个资源；文本原样回来，图片与二进制按端点能力上传或内联，不丢块 |
| `get_mcp_task_result` | `server`、`task_id` | 按任务 id 取回一个任务的结果（见下一节） |
| `cancel_mcp_task` | `server`、`task_id` | 让服务器停掉一个已经发起的任务 |

`load_skill` 与 `call_skill_sub_agent` 不是 MCP 的工具：它们来自技能那一侧，与服务器无关，别混进这张表。

权限有两处要分开看。这五条工具名恒向 `tools` 维度报名，于是「不许调 MCP」可以是很干净的一刀；而哪几台服务器算数归 `mcps` 维度，按服务器名匹配。`call_mcp_tool`、`read_mcp_resource` 与两条任务工具还各自按本容器的白名单判一次服务器名：连接管理器是全局共享的，只按「连上没有」判，会让任一 `Agent` 连上的服务器对别的容器也敞开。

文本有输出保护，媒体没有。一整个答复里的文本加起来超过 `maxToolOutput`（缺省 32768 字符）时，全部文本落盘为 `result.txt`，回给模型的是一段说明加头尾各 1000 字符的预览；判定用的是全部文本的字符总数，不是逐块判 —— 逐块判的话，几个各三万字的块合起来能把请求灌爆。图片、音频这些不受这条规则管：它们按端点能力上传成 `file_id` 或内联成 base64，位置保持原样。

## 任务

任务是 MCP 调用里那种耗时长的形状：服务器接下调用之后先交一个句柄，结果稍后按 id 取，进度靠反复问。

谁决定用不用任务，这件事在 2026-07-28 那一版里反过来了：**服务器说了算**，客户端只声明自己接得住。工具在清单里用 `execution.taskSupport` 说明它怎么对待任务，我们按它提一个偏好：

| 档位 | 我们怎么发 |
|---|---|
| `forbidden`（不写这一格也是这档） | 不带任务参数，同步调 |
| `optional` | 提议成任务，但服务器可以照旧同步跑完 |
| `required` | 一定提议成任务：不带任务参数服务器会拒 |

偏好只是我们这一侧的话；应答到底是一个结果还是一个句柄，由服务器定。这一层由官方扩展轨道的 `@modelcontextprotocol/ext-tasks` 承担（Beta，目标进核心），我们只包了一层：每条连接一个任务会话，把「当场结果」与「任务句柄」两条路分开。

走任务的那一次，`call_mcp_tool` 立刻交回一个句柄，不在这里等结果：

```json
{ "task": true, "taskId": "...", "hint": "..." }
```

终态到了就往发起那次调用所在会话的 inbox 投一条（`completed` / `failed` / `cancelled`）。中间状态不投：那不是「有事要人动手」，每条都投就是刷屏。投递口是 `McpTaskNoticePort`，由宿主实现：`sessionOf(agent)` 说调用方属于哪段会话，`deliver(sessionId, notice)` 把通知放进它的 inbox。投递不创建、不复活会话：那段已经不在就把通知丢掉并留一行日志。

结果本身用任务 id 取：`get_mcp_task_result`。服务器存下来的就是一次工具调用的结果，所以它走与 `call_mcp_tool` 同一套媒体映射与输出保护；任务还没跑完的话这里会等它跑完。放弃就 `cancel_mcp_task`，能不能停下来由服务器说；不管停没停，终态通知照旧会到。

几条边界：

- 任务 id 只在它自己那台服务器上唯一，所以手里的句柄与服务器的对应关系按「服务器 + 任务 id」记。
- 这份对应关系只活在进程里：进程没了就没了 —— 任务本身在服务器那边，重启之后再来取结果会拿到一句「没这个任务」。连接一断，这台服务器上的任务会话跟着关。
- 发起调用的若是被派出去的 `SubAgent` 或一次性 `Agent`，`sessionOf` 回 `undefined`：句柄照旧拿得到、结果照旧拉得回来，只是没有那条「任务结束了」的通知 —— 没有会话可以回报。
