# 宿主

宿主是一个常驻进程：持有数据库、会话、工作区、资产与凭证，在回环地址上提供接口。它不思考，也不调用模型——那是 agent 的事。它负责让会话存在、让 agent 有地方被装起来、让多个客户端看到同一份事实。

## 启动

```bash
node packages/host/dist/cli.js serve                 # 本机实例，只监听 127.0.0.1:8790
node packages/host/dist/cli.js serve --public        # 对外实例，监听所有网卡
node packages/host/dist/cli.js serve --port 9000 --host 127.0.0.1
node packages/host/dist/cli.js serve --ai-zen-dir /srv/ai-zen
```

启动后打印五行：监听地址、版本、发现文件、日志目录、凭证文件。已经有一台在服务时，本进程打印它的地址后退出，不抢端口。

数据根由 `AI_ZEN_DIR` 或 `--ai-zen-dir` 决定，缺省 `~/.ai-zen`：

```
~/.ai-zen/
├── config.json        端点、模型、默认模型、上下文阈值、刷新时机等
├── agents/            agent 定义
├── sub-agents/        子代理定义
├── skills/            技能
├── tools/             用户工具
├── mcp.json           MCP 服务器
├── ai-zen.db          会话、消息、输入队列、工作区、资产、凭证、通知
├── logs/
└── run/
    ├── host.json      此刻谁在服务（地址、端口、pid）
    ├── token          本机客户端的凭证明文
    └── next-version.json  下次该跑哪一版
```

## 凭证

| 场景 | 怎么办 |
|---|---|
| 本机客户端 | 启动时宿主把一串能用的凭证明文写进 `run/token`，客户端直接读 |
| 别的设备 | `token create --note <说明>` 造一串，明文只在那一次输出里出现，手工分发给那台设备 |
| 查看与吊销 | `token list`、`token revoke <id>` |

数据库里存的是摘要，创建之后再也读不回明文。本机那一串在重启时不会被换掉：只要库里还认它，就继续交付，否则客户端上次读走的那串会随宿主重启一起失效。

## 会话

一段会话是数据库里的一行，加若干条消息。它永远存在，进程重启、agent 终结都不影响它。

| 字段 | 含义 |
|---|---|
| `agentId` | 用哪份定义 |
| `modelId` | 这一段用什么模型；`null` 表示当前指不到任何可用模型 |
| `thinkingLevel` | 思考档位；`null` 表示跟随定义 |
| `autoHandoff` | 撞上软线时自动交接，还是先问一句 |
| `handoffThreshold` / `guardThreshold` | 会话级的阈值覆盖；`null` 表示用模型定义上的值 |
| `lineage` | 谁开的这一段；`null` 表示用户建的 |
| `name`、`nameSource` | 名字，以及它从哪儿来（占位、自动、用户、交接存档） |

工作区是一个目录。会话属于一个工作区，它的 agent 就在那个目录上干活：`cwd` 决定能力目录的解析、也决定交接文档落在哪。

## 唤醒与投递是两件事

| 动作 | 做什么 | 不做 |
|---|---|---|
| `agent.wake` | 从数据库读出材料，把这段会话装成一个 agent，登记，开跑 | 不投递任何东西，不新建会话 |
| `agent.send` | 把一条内容投进活着的那段会话 | 不创建、不复活会话；没有 agent 时返回 `not_found` |

因此客户端要先唤醒再投递。唤醒只填补「行在、agent 不在」这一格：一段会话在被使用之前没有 agent，进程退出后也没有——历史在数据库里，下一次唤醒时按「历史 + 还没取走的输入」装回同一个上下文，队列里剩下的那几条也放回去。

唤醒是幂等的：已经活着就把同一个 agent 交回来；正在装的话，两个同时到达的唤醒等的是同一次装配，不会装出两个 agent 写同一份记忆。

## 会话之间

宿主把运行时装起来时注入三个工具的能力：`create_session`、`post_message`、`read_session_status`。

- 平级：开出来的那一段有自己的历史、工具与模型
- 单向阻止套娃：被开出来的那一段只少了 `create_session`，只能开一层
- 不阻塞：`post_message` 投递完成即返回，对方在忙也照投，它在对方下一次工具间隙被取走
- `read_session_status` 只回答忙闲、名字与最近一句，不搬历史

投不进去时返回两种原因：`gone`（这段会话不在了）、`dead`（行还在，只是没有活着的 agent）。

## 客户端接入

`@ai-zen/agents-client` 是「连哪儿、拿什么进门」的唯一实现：

1. 显式地址（`--server` 或 `AI_ZEN_SERVER_URL`）与显式凭证（`AI_ZEN_SERVER_TOKEN`）优先
2. 否则读数据根下的 `run/host.json` 与 `run/token`
3. 探不到宿主就拉起一个：调用方给了宿主入口就起那个入口（桌面端把宿主打进自己的产物），否则 `npx -y @ai-zen/agents-host@<版本范围> serve`
4. 拉起之后轮询地址，直到开始监听

`run/next-version.json` 是升级的落点：宿主不自己拉起自己，下次该跑哪一版只能落在文件上，由启动方式去读。盘上有 pin 时按它拉，没有才用客户端自带的版本范围。

## 题与通知

两样东西都落在会话上：

- **通知**：失败、越线、交接结束这类事实，进数据库的 `notice` 表，客户端连上就能看到历史
- **题**：需要人做决定时（撞上交接软线时选哪种方式、MCP 服务器要求填表），宿主挂一道题并等答复。题只做实时，不落库：进程没了这一趟也就没了，没有第二张表

一次性调用（`ai "…"`）没有人可以问，因此那条路上不挂题板——题会一直挂着，而不是替用户选一个选项。

## 接口

回环地址上的 WebSocket，协议是 tRPC。会话、消息、队列、配置、MCP、凭证、资产、搜索、交接各是一组 procedure。这层没有 HTTP 页面，也不提供静态资源：它只为客户端服务。

消息进 FTS5 全文索引（关键词短到索引搜不到时退回子串匹配）；会话按名字搜索，名字不进索引，是一条扫描全表的 `LIKE`。

## 对外实例

`--public` 使宿主监听所有网卡，供本机之外的客户端连接。此时：

- 凭证不再写 `run/token`，只能由人执行 `token create` 拿到明文再分发
- 宿主只说明文 WebSocket，不提供 TLS；要加密就在前面套一层反向代理
- 升级用 `run/next-version.json`：写入目标版本，下一次启动方式读到它就拉那一版
