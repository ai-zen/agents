# 线上协议

这一页是照着实现一个客户端时逐条对照的规范。传输是 **WebSocket**，消息是 **JSON-RPC 2.0**。协议版本是 `2`：版本对不上就不建连。

条文只回答「允不允许」，不回答「发不发、用不用」——后者是实现的选择。

## 传输

- 服务端在一条 **WebSocket** 连接上收发。
- **一条 WebSocket 消息就是一条完整的 JSON-RPC 2.0 消息**，两个方向都是如此。
- 消息边界只有 WebSocket 消息边界这一个来源：文本帧里**不留结尾换行**，一条消息在一条 WS 消息里开始并结束。

## 消息分类

一条消息属于哪一类，只看它有没有 `method` 和 `id`：

| 形状 | 是什么 |
|---|---|
| 有 `method` | 请求（带 `id` 就是调用，回响应） |
| 无 `method`、有 `id` | 响应 |
| 有 `method`、无 `id` | 通知（不回响应） |

`session.event` 是服务端发的通知：有 `method`，无 `id`，客户端不回。

**客户端发来的通知一律静默丢弃**：有 `method`、没有 `id` 的消息，服务端不派发、不回任何东西 —— 连错误响应都不回 —— 连接照旧。这是 JSON-RPC 2.0 原文的规定：规范里通知就是「不求回执」的那一类，服务端 MUST NOT reply to a Notification，回一条错误反而是违反标准。丢弃也不改动连接状态：它不算「第一条请求」，握手门等着的仍然是下一条带 `id` 的 `hello`。

本版服务端不主动发请求，所以客户端收不到响应、也不该发出响应：服务端收到的消息里**没有 `method`** 就是非法请求（见下文的「`invalid-request` 管的五种情况」）。

## `id`

`id` 是**整数，取值 `0 … 2³²-1`**（含两端）。

JSON-RPC 2.0 允许 `id` 是字符串或数字、也允许 `null`；这一版只有整数。原因是二进制帧（见下）把 `id` 放在消息开头的 4 个字节里，字符串放不进去。

## 文本帧与二进制帧

| 帧 | 内容 |
|---|---|
| 文本帧 | 一条 JSON-RPC 2.0 消息（请求 / 响应 / 通知） |
| 二进制帧 | 某条请求的载荷 |

二进制帧的字节布局：

```
字节 0…3    该请求的 JSON-RPC id（大端序、无符号整数）
字节 4…末   原始载荷（无分隔符、无编码）
```

- 前 4 字节是该请求的 JSON-RPC `id`（大端序、无符号整数），其余是原始字节。这就是 `id` 被限定在 `0 … 2³²-1` 的那条约束的出处。
- 载荷的关联**只靠这 4 个字节**，不靠「它紧跟在谁后面」：同一条连接上可以有多条带载荷的请求同时在飞，每块二进制帧各自按那 4 个字节找到自己那条请求。
- 字节不进 JSON：`params` 里不带字节，字节只走二进制帧。图片、文件这类要交给服务端处理的内容走这条路（`content.upload`，见下一节）。
- 一条请求最多配**一块**二进制帧。

### 次序：二进制帧晚于它的请求帧

WebSocket 在**单条连接上保序**：先发出的消息先到。于是有一条可以依赖的次序 —— **二进制帧必然晚于它的请求帧**：请求帧先到，服务端把它登记成「在飞」的那一条；字节随后到，按那 4 个字节的 `id` 找回这条请求。

反过来说：**二进制帧早于它的请求帧就是违规 → 断开连接**。它只可能来自实现错误（`id` 记错了、或者压根没先发请求）。

这条次序是下一节「找不到在飞请求就断连」那条判据的依据：既然字节必然在后面到，「`id` 找不到在飞请求」就只剩一种解释 —— 两端对「哪块字节属于谁」已经分叉，而不是「请求还在路上」。所以不必等待、不必缓冲、也不必重试。

### 二进制帧的异常分支

四种情况，三条断连、一条不断：

| 情况 | 结果 | 为什么 |
|---|---|---|
| 前 4 字节的 `id` **找不到对应的在飞请求** | **断开连接** | 错误归不到任何请求 —— 连「回给谁」都不知道，无从回复。字节必然晚于它的请求帧（见上一节「次序」），所以这种帧只可能来自实现错误 —— 两端对「哪块字节属于谁」已经分叉 |
| **同一个 `id` 收到第二块**二进制帧 | **断开连接** | 一条请求只带一块载荷。第二块说明两端对请求与载荷的配对理解已经不一致，同上，无从回复 |
| **不足 4 字节**（连 `id` 都读不出来） | **断开连接** | 读不出 `id` 就归不到任何请求 —— 与「`id` 对不上」同类：无从回复，只可能来自实现错误 |
| **空载荷**（只有那 4 字节、后面没有字节） | 连接**不断开** | 这是一块**对齐**的帧：边界清清楚楚，只是内容为空。它是不是合法的载荷由方法自己判 —— `content.upload` 会回 `bad-params` |

一句话区分：断连的那三条都是「这串字节归不到任何请求」（读不出 `id` / `id` 对不上 / 同一 `id` 的第二块），不断的那一条是「字节对得上请求，只是空」。

## `content.upload` 与二进制通道

`content.upload` **名字不变**，仍是方法名，命名空间也还是 `content.*`。变的只有一处：

- **它的字节不再通过 `params` 里的长度声明挂在请求帧后面**，而是由**一条独立的二进制帧**承载，那条帧开头的 4 个字节就是这条请求的 `id`。
- 形状是「一次调用、两条 WS 消息」：先一条文本帧，是 `content.upload` 的普通请求（带 `id`）；再一条二进制帧，前 4 字节是同一个 `id`，其后是原始字节。服务端按 `id` 把两者拼成一次调用再派发。
- **字节一律不进 JSON**：`params` 只说这件事是什么，里面也没有任何长度字段 —— 二进制帧自己有多长，载荷就有多长。
- 一条请求配一块二进制帧，不多不少（第二块 → 断连；空载荷 → 方法自己判，见上一节）。

`params` 的字段就三个，**都必填**：

| 字段 | 类型 | 必填 | 是什么 |
|---|---|---|---|
| `sessionId` | string | 是 | 这批内容要发给哪一段会话（端点与视觉能力由这段会话实际使用的模型决定） |
| `mime` | string | 是 | 字节的 MIME（`image/png` / `application/pdf` …） |
| `filename` | string | 是 | 文件名（上传到 Files API 与 `file` 块都用它） |

它是**二进制通道唯一的真实用例**：服务端的二进制方法名单里只有它，而名单是「线上会多一段字节」的唯一凭据 —— 这类方法在收到字节之前不会被派发。

## 大小上限

| 上限 | 值 | 落在哪儿 |
|---|---|---|
| WebSocket `maxPayload` | **64 MiB** | 一条 WebSocket 消息（文本或二进制） |
| 文本帧 | **8 MiB** | 一条 JSON-RPC 文本消息 |

判定次序是 **先 WebSocket 层、再实现层**，两档各管一侧，不互相污染：

1. WebSocket 层先按 `maxPayload` = **64 MiB** 兜底：任何一条 WS 消息（文本或二进制）超过它，就是超限。这一层不知道帧里的内容是什么。
2. 文本帧在**实现层**再单独卡 **8 MiB**：一条 JSON-RPC 文本消息超过它，就是超限。
3. **二进制帧可以到 64 MiB**，不受那 8 MiB 约束 —— 图片、文件的字节没有理由被「文本消息」那条线卡住。

超限的结果是**直接断开连接，不先发错误响应**。它和「不是合法 JSON」不是一类事：那条是「这条消息的内容不成立」，这一条是「这条消息在体积上不被收下」—— 64 MiB 那档在 WS 层装配时就被拒，一条完整的消息从未存在过，也就没有可回应之物；8 MiB 那档在实现层量到长度就已经越过上限。两档都没有「改一次请求再试」的恢复路径（同一段内容再发一遍还是这么大），所以断连是唯一能让两端都确定下来的结局。

## 不支持批量

本版不支持 JSON-RPC 的 batch：顶层是数组的消息不是合法请求，服务端回**一条** `-32600` 错误响应（`data.code: "invalid-request"`），不逐项展开，**连接不断开**。

## `params` 只接受对象形式

`params` 只接受对象形式（by-name）。数组形式（by-position）回 `-32602`（`data.code: "bad-params"`）。

## 方向

本版服务端只发通知，不主动发请求。请求由客户端发起，服务端回响应并推送 `session.event`。

## 握手

握手的方法名是 `hello`，它是方法表里的一条普通方法（不是独立的一类帧）：带 `id` 发，服务端按普通响应回。

请求（客户端 → 服务端）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "hello",
  "params": {
    "protocol": 2,
    "client": { "name": "ai", "version": "1.4.0" }
  }
}
```

响应（服务端 → 客户端，成功时）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "name": "agents-server",
    "version": "0.1.0",
    "protocol": 2,
    "pid": 48213,
    "startedAt": "2025-01-01T00:00:00.000Z"
  }
}
```

`result` 是**扁平**的，没有 `server` 这一层：这一版没有 `ok` 了 —— 成功与否由「回的是 `result` 还是 `error`」表达 —— 既然 `result` 里不再需要和 `ok` 分家，也就没有需要用命名空间隔开的兄弟字段，再包一层只是白多一层。

字段名是冻结的：

| 位置 | 字段 | 类型 | 是什么 |
|---|---|---|---|
| `params` | `protocol` | number | 客户端支持的协议版本（本版 `2`） |
| `params` | `client.name` | string | 客户端名字（只用于日志与本机调试，不参与鉴权） |
| `params` | `client.version` | string | 客户端版本 |
| `result` | `name` | string | 服务端名字 |
| `result` | `version` | string | 服务端版本 |
| `result` | `protocol` | number | 服务端这边的协议版本（本版 `2`） |
| `result` | `pid` | number | 服务端进程号 |
| `result` | `startedAt` | string | 服务端启动时刻（ISO 时间字符串） |

这两个形状的类型定义处是 `packages/server/src/protocol/messages.ts` 的 `HelloParams` / `HelloResult` —— `hello` 就是方法表（`MethodApi`）里的一条，走的是和别的方法一样的请求 / 响应通路。

规则：

- **第一条消息必须是对 `hello` 的请求**。握手之前调用别的方法 → 回 `-32000` + `data.code: "handshake-required"`，**连接不断开**；补上 `hello` 就能接着用这条连接。
- **`params` 不是对象**（包括压根没给 `params`）→ 回 `-32602` + `data.code: "bad-params"`，**连接不断开**。它不是版本不匹配：那是「这条请求的壳不对，改一下再发」，不是「两端说的不是一代协议」。
- 协议版本不匹配 → `data.code: "version-mismatch"`（`-32000`），随后**断开连接**。`params.protocol` 缺失或不是数字也落进这一格 —— 读不出对端的版本，等于对不上。
- 握手完成之后**再发一次 `hello`** → 回 `-32600` + `data.code: "invalid-request"`，**连接不断开**（它落进下文「`invalid-request` 管的五种情况」的第五格）。
- 没有例外：即使本版还没有鉴权，也照样先握手。这样将来加鉴权时，改的是握手这一段，不是所有客户端的建连流程。

## 错误

响应形状（`error` 与 `result` 二选一，不共存）：

```json
{
  "jsonrpc": "2.0",
  "id": 7,
  "error": {
    "code": -32000,
    "message": "handshake required",
    "data": { "code": "handshake-required" }
  }
}
```

- `code` 是**数字**，按 JSON-RPC 的标准码取；`message` 是**给人看**的字符串，客户端不拿它做判据；`data.code` 是**稳定的字符串码**，客户端拿它做判据。

### 数字码映射

| `data.code` | `code` | 什么时候出现 |
|---|---|---|
| `bad-frame` | `-32700` | 文本帧**不是合法 JSON**（只有这一种情况用这个码） |
| `invalid-request` | `-32600` | 是合法 JSON，但**不是合法请求对象**（顶层数组 / 缺 `method` / 缺 `jsonrpc: "2.0"` / `id` 不合规 / 握手后再发 `hello`） |
| `unknown-method` | `-32601` | 方法名不认识 |
| `bad-params` | `-32602` | 参数形状不对 |
| `internal` | `-32603` | 服务端内部错误 |
| 其余全部（业务码，以及 `bad-handshake` / `version-mismatch` / `handshake-required`） | `-32000` | 业务失败、握手相关的请求级失败 |

字符串码的全表在服务端 `packages/server/src/protocol/errors.ts`。

### `bad-frame`：不是合法 JSON 只是一个可恢复的错误

文本帧不是合法 JSON → 回 `-32700` + `data.code: "bad-frame"`，**连接不断开**。

理由正是传输换成 WebSocket 之后变掉的那条假设：**消息边界已经由 WebSocket 给出**。按行分帧的年代，「帧边界」与「能否解析」是同一件事 —— 一行解析不出 JSON，就不知道下一行从哪儿算起，后面的字节再也读不准，那才叫流错位。现在不是：一条 WS 消息在哪儿结束，与它里面装的是什么无关；读完这一条，能稳稳地接着读下一条。

所以「不是合法 JSON」只是一条消息的内容不成立，不是这条流坏了。用断连去惩罚一个可恢复的错误，会连带丢掉那条连接上其它在飞的请求 —— 代价与错误本身完全不成比例。

### `invalid-request` 管的五种情况

同一个字符串码管五件事，五者都是 `-32600` + `data.code: "invalid-request"`，且**都不断开连接**：

| 情况 | 为什么归到这里 |
|---|---|
| 顶层是**数组**（本版不支持批量） | 数组不是合法的请求对象 |
| 合法 JSON 但**缺 `method`** | 本版服务端不发请求，客户端也不会收到、更不该发出响应，所以一条没有 `method` 的消息什么都不是 |
| **缺 `jsonrpc: "2.0"`** | 外壳不是 JSON-RPC 2.0：这条消息不是按这套规则写的，它的 `id` 与 `method` 也就无从按这套规则读 |
| **`id` 不合规**（非整数 / 负数 / 超过 2³²-1） | `id` 只有那一段整数可用（见「`id`」）：越界的那个数挂不回任何请求，也装不进二进制帧的 4 字节前缀 |
| **握手完成之后再次发 `hello`** | `hello` 只在握手那一刻有意义；第二次不是一次合法的调用 |

五者的共同点：**流都还是对齐的** —— 每条消息在 WS 边界上清清楚楚地开始并结束，读完这一条能接着读下一条，所以没有断连的理由。它们只是「这条消息不是一次合法调用」，因此用错误响应回答。

`id` 分两种情况：前四种根本归不到任何请求（连「你问的是哪件事」都读不出来），回 `id: null`；第五种本身就是一条对得上号的请求（它带着自己的 `id`），错误就挂回它自己的 `id`（见下一节）。

`bad-frame` 只表示「不是合法 JSON」这一件事；能解析出的对象一律不再叫 `bad-frame`。

### 错误响应的 `id`

错误响应和成功响应一样带 `id`；取值只有两种：

| 什么时候 | `id` |
|---|---|
| 顶层是数组、缺 `method`、缺 `jsonrpc: "2.0"`、`id` 不合规 | `null` |
| 其余所有错误响应（含握手之后重发 `hello`） | 数字 —— 就是触发它的那条请求的 `id` |

`null` 是 JSON-RPC 2.0 为「无法确定 `id`」规定的用法：这几种情况下那条消息根本不构成一次请求，归不到任何 `id` 上。除此之外每一条错误响应都能追溯到具体的那条请求，`id` 恒为数字 —— `hello` 之后重发 `hello` 也一样，那次 `hello` 是带 `id` 发来的。

客户端侧的对偶规则：**丢弃 `id` 不在自己在飞表里的响应**。客户端的在飞表里只有整数 `id`，所以 `id: null` 的错误响应同样落进这一格 —— 它说的是「你刚发的那条消息不是合法请求」，但既然没有对应的在飞调用，就没有调用方可以递过去；收到就丢，不改连接状态、不当致命错误。

### `data.code` 必须存在

JSON-RPC 2.0 里 `error.data` 是可选的；这一版**每一条错误响应都带 `data.code`**，它是客户端唯一能依赖的错误标识。

客户端必须能容忍不认识的字符串码：**原样递给调用方**，不得把它当致命错误、不得因此断开连接。新码是加出来的，不是把旧码改名。

## 事件

15 个事件统一走**一条 method `session.event`**。它是通知（无 `id`），`params` 就是对应的事件对象，靠 `event` 字段区分：

| `event` | 谁产生 | 是什么 |
|---|---|---|
| `open` | core | 一轮开始 |
| `chunk` | core | 正文增量 |
| `parsed` | core | 消息解析完成 |
| `tool-call-end` | core | 工具结果定型 |
| `error` | core | 出错 |
| `finally` | core | 收尾 |
| `sub-agent-start` | core | 子 Agent 开始 |
| `sub-agent-end` | core | 子 Agent 结束 |
| `session-phase` | 服务端 | 阶段变化 |
| `session-turn-end` | 服务端 | 一轮结束 |
| `session-notice` | 服务端 | 会话内通知 |
| `session-question` | 服务端 | 题目 |
| `session-id-changed` | 服务端 | 会话 id 变了 |
| `session-title-changed` | 服务端 | 会话标题变了 |
| `server-notice` | 服务端 | 全局通知（不属于任何会话） |

`params` 里的其余字段由该事件的类型决定。形状示例（只画必要部分）：

```json
{ "jsonrpc": "2.0", "method": "session.event", "params": { "event": "chunk" } }
```

### 保序

- 事件在**单条连接上保序**：同一条连接收到的顺序就是服务端发出的顺序。
- 顺序有语义：`open` → `chunk` … → `parsed` → `tool-call-end` → `finally`。
- 还有两条硬的：`error` 早于 `finally`；`finally` 早于 `session-turn-end`。`finally` 与 `session-turn-end` 是两条不同的事件，不是改名关系。

## 有状态的通知与题目

题目、会话内通知、全局通知都是**有状态、有生命周期**的槽位，不是「发一次就没了」的广播：没人在线的时候也要先登记下来，后来接上的人能补看，确认之后才消失。

| 东西 | 挂在谁身上 | 活到什么时候 | 落盘 | 查询入口 |
|---|---|---|---|---|
| 题目 | 会话 | 随会话消失 | 不落盘 | `session.snapshot` 的 `pendingQuestions` |
| 会话内通知 | 会话 | 随会话消失 | 不落盘 | `session.snapshot` 的 `pendingNotices` |
| 全局通知 | 服务端进程 | 随进程消失 | 不落盘 | `notice.list` |

三条共同规则：

- **显式确认才消失**：没有任何计时器会把它自动消掉。
- **一份状态**：任意一条客户端确认即消，服务端不按客户端各存一份已读。
- **id 是 UUID**：题目 id 与通知 id 都是 UUID，跨进程、跨 daemon、跨重启都不重。它们与请求的 `id` 不是一回事 —— 请求 `id` 是 `0 … 2³²-1` 的整数。

槽位里装的**就是事件对象本身**，不另造一套「槽位元素」结构；两类通知的载荷里都带 `id`（UUID），所以推送的那一条与槽位里的那一条是同一个 id。唯一多出来的字段是全局通知的 `createdAt`（它挂不到别的东西上，得自己记一笔登记时刻）。

### 题目

题目推一条 `session-question` 事件。

`session.snapshot` 的 `pendingQuestions` 是 `SessionQuestionEvent[]`，元素含：

| 字段 | 类型 | 是什么 |
|---|---|---|
| `event` | `"session-question"` | 判别字面量 |
| `sessionId` | string | 属于哪一段会话 |
| `questionId` | string（UUID） | 回答时带回来的那个 id |
| `kind` | `SessionQuestionKind` | 哪一类问题（客户端据此查自己的词典与分派表） |
| `input` | `"select"` / `"text"` | 怎么答：选一个还是填一个值 |
| `options?` | `string[]` | `input: "select"` 时的选项 id 列表（文案在客户端） |
| `params` | object | 渲染标题要用的事实 |
| `allowSkip` | boolean | 用户能不能「不答」 |
| `fallback` | `string \| null` | 等不到答案时服务端会用的取值 |

回答用 `session.answer`，参数只有两个字段：

```json
{ "jsonrpc": "2.0", "id": 12, "method": "session.answer",
  "params": { "questionId": "<uuid>", "choice": "<某个选项>" } }
```

- `choice` 是 `string | null`：`null` = 跳过，**仅当** `allowSkip` 为真时可用。
- 只认 `questionId`，**不带 `sessionId`** —— 题目 id 是 UUID，自己就够定位。
- 还没被回答的题目留在**会话的槽位**里，`session.snapshot` 的 `pendingQuestions` 列得出来。

### 会话内通知

会话内通知推一条 `session-notice` 事件。

`session.snapshot` 的 `pendingNotices` 是 `SessionNoticeEvent[]`，元素含：

| 字段 | 类型 | 是什么 |
|---|---|---|
| `event` | `"session-notice"` | 判别字面量 |
| `sessionId` | string | 属于哪一段会话 |
| `id` | string（UUID） | 这条通知的 id，确认时用它（`notice.ack`） |
| `level` | `"info"` / `"warn"` / `"error"` | 严重程度 |
| `code` | `SessionNoticeCode` | 哪一个通知（客户端据此查自己的词典） |
| `params?` | object | 文案里的可变部分（客户端代入自己的模板） |

还没被确认的留在**会话的槽位**里，`session.snapshot` 的 `pendingNotices` 列得出来；确认走 `notice.ack`，和全局通知是同一条方法（见下一节）。

`id` 与全局通知的 `id` 是同一套 UUID。**实时推送与槽位是同一个东西的两个出口，id 一致** —— 所以实时推过来的那条 `session-notice` 可以直接拿去 `notice.ack`，不用回头再查一次列表。

### 全局通知

全局通知推一条 `server-notice` 事件，它**不属于任何会话**，所以挂在进程上而不是会话上 —— 换一段会话不会把它带走。实时推送的那条 `server-notice` 事件的载荷里也带 `id`（UUID），和 `notice.list` 列出的槽位是同一个 id —— 理由同上：推送与槽位是同一个东西的两个出口。

查询与确认是独立的一对：

- `notice.list` 列出此刻还没消失的那些；
- `notice.ack { ids }` 按 id 确认。

`notice.list` 的结果是 `notices: GlobalNoticeSlot[]`，元素含：

| 字段 | 类型 | 是什么 |
|---|---|---|
| `id` | string（UUID） | 这条通知的 id，确认时用它；推送的那条与这里的槽位是同一个 id |
| `level` | `"info"` / `"warn"` / `"error"` | 严重程度 |
| `code` | 与 `server-notice` 同一套码 | 哪一个通知 |
| `params?` | object | 文案里的可变部分 |
| `createdAt` | string（ISO 时间字符串） | 什么时候登记的 |

```json
{ "jsonrpc": "2.0", "id": 13, "method": "notice.ack", "params": { "ids": ["<uuid>", "<uuid>"] } }
```

`ids` 里可以混着放**全局通知与会话内通知**的 id：id 是 UUID、全局唯一，服务端先查全局表、再扫各会话的通知表，两处都认 —— 会话内通知因此不必另开一条确认方法。

`notice.ack` 的结果是 `{ acked: string[] }` —— **真正被删掉的那些 id**（两类都算）。本来就不存在、或者已经被别人确认掉的 id **不会**出现在里面；客户端据此知道哪些还没消，而不是收到一句「行」。

`notice.list` / `notice.ack` 是一个**独立的 `notice.*` 命名空间**，定义在 `packages/server/src/protocol/notice.ts`（`notice.list` 只列全局的 —— 会话内通知有所属物可依附，走快照；而确认是两类共用的同一条 `notice.ack`）。

加上 `hello` 与这两条，线上方法一共 **48** 条（45 + `hello` + `notice.list` + `notice.ack`），事件仍是 **15** 条。

### 实时推送与补看是两条并行的路

- **实时推送**：产生的那一刻立刻推一条通知（`session-question` / `session-notice` / `server-notice`），在线的客户端不用等下一次查询。
- **补看**：槽位与查询入口是兜底 —— 产生时没人在线、断线重连、换一条连接甚至换一台客户端接上，都靠 `session.snapshot`（题目、会话内通知）或 `notice.list`（全局通知）拿到还没消失的那些。

两条路读的是同一份状态，因此「推过」与「还在」是两件事：推过的可能已经被别人确认掉；没推过的（产生时没人在线）也可能还在。

## 什么时候断开连接

断连的完整清单如下，**只有六种**：

| # | 情况 | 结果 |
|---|---|---|
| ① | 一条 WS 消息超过 `maxPayload`（**64 MiB**，文本与二进制同吃这一条线） | **WebSocket 层**直接断开，**不先发错误响应** |
| ② | 一条**文本**消息超过 **8 MiB**（实现层单独卡的档） | 断开连接，**不先发错误响应** |
| ③ | 握手阶段协议版本不匹配 | 先回 `version-mismatch`，随后断开 —— 断代，不做竭力兼容 |
| ④ | 二进制帧的 `id` 找不到在飞请求 | 断开连接 |
| ⑤ | 同一个 `id` 收到第二块二进制帧 | 断开连接 |
| ⑥ | 二进制消息**不足 4 字节**（连 `id` 都读不出来） | 断开连接 |

六条的共同性质：**这些情形下这条连接再也无法继续。** ①② 是那条消息在体积上就没被收下（同一段内容重发一遍还是这么大，没有「改一次请求再试」的恢复路径）；③ 意味着两端说的不是一代协议，后面每条消息的形状都不可信；④⑤⑥ 是两端的字节视图已经分叉、或者根本读不出归属，三类都归不到任何请求，连「回给谁」都没有。

除此之外没有任何断连：非法 JSON（`bad-frame`）、未知方法、`params` 形状不对、`hello` 的 `params` 不是对象（`bad-params`）、握手之前调用别的方法（`handshake-required`）、握手之后重发 `hello`、顶层是数组、消息缺 `method`、缺 `jsonrpc: "2.0"`、`id` 不合规、业务失败、空载荷的二进制帧、客户端发来的通知（静默丢弃，连错误都不回）—— **一律不断开**；客户端侧遇到不认识的 `data.code` 也原样交给调用方，不断开。
