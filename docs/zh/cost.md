# 花费

模型调用按请求计费。成本只有两个来源：请求的次数，与每次请求的输入长度。

第二项是这本运行时里最容易被忽略的一处：每次请求都要重发完整历史，因此一段会话的成本随历史长度增长，而不是随对话轮数线性增长。所以「不让历史无限变长」与「不让每次请求变长」是两条独立的事，下面分开写。

## 不让每次请求变长

| 机制 | 事实 | 省在哪里 |
|---|---|---|
| 前缀缓存 | 请求体按白名单重建：只留 `role`、`content`、`tool_calls`、`tool_call_id`、`function_call`、`reasoning_content`，不带消息 id 与时间戳。同一段对话的发送前缀因此逐字节稳定 | 服务方按前缀命中缓存时，已缓存的那一段按更低的价计费 |
| 稳定上下文标识 | 端点声明了 `providerSessionHeader`（如 `x-opencode-session`）时，每个活 agent 的每一条请求都带同一个标识。宿主用会话 id，进程重启后不变；派出去的子代理有自己的标识 | 服务方据此把同一段上下文的请求路由到一起，缓存才可能命中 |
| 渐进式披露 | 技能正文、MCP 远端工具、子代理细节都不进工具清单，清单里只有入口 | 装几十台 MCP 服务器、几十个技能，清单长度不变 |
| 工具输出上限 | 单次工具输出超过 `maxToolOutput`（缺省 32768 字符）时，超长的那一段不整段进上下文：`exec` 这类工具把全文落盘到临时目录，模型只拿到头尾预览与文件路径 | 一次 `pnpm test` 的几万行日志不会变成之后每一条请求都要重发的内容 |
| 委派隔离 | 子代理有自己的历史与工具，父那一侧只收到它最后一条内容，以及累加后的 `subAgentUsage` | 子代理中间几十次工具调用不进父的上下文 |
| 辅助请求另算 | 会话自动起名与交接摘要走 `completeOnce`：不流式、不带工具、可以指定比主模型便宜的模型。起名只发送最近 2000 字符 | 几十 token 的活不用主模型的一次全量输入来干 |

## 不让历史无限变长

| 机制 | 事实 | 省在哪里 |
|---|---|---|
| 两条阈值 | `handoff` 软线与 `guard` 硬线，出厂是窗口的 40% 与 80% | 在历史变成两倍、三倍之前就换手，而不是等到装不下 |
| 越线不发 | 硬线之上 `ContextGuardPlugin` 在 `onInnerLoopStart` 返回理由，这一次请求根本没发出去 | 不为一次注定失败的请求付费 |
| 交接 | 记忆换成「模板 + 一条只带路径的断点消息」 | 换完之后每一条请求只携着模板与一条短消息 |
| 中断不重来 | `abortedMessageStrategy: keep` 保留已输出的半截回答，下一次接着往下说；`abortedToolRoundStrategy: fill` 让工具轮次整轮留下，不整段重做 | 一次中断不会让已经烧掉的输入白费 |

## 不让请求次数变多

| 机制 | 事实 | 省在哪里 |
|---|---|---|
| 结果投回 | `async_exec`、`async_timeout`、MCP 长任务的结果到达时投回会话，把 agent 从空闲唤醒 | 不必用 `sleep` 反复轮询——每次轮询都是一整笔全量输入 |
| 队列不丢投递 | 处理过程中投进来的话进队列，按优先级排队 | 不需要「等它跑完再发」这类由用户侧重试的动作 |

## 可查

每条 assistant 消息上带着产生它的那次请求的 token 用量（`usage`）；一次委派跑完，子代理及其孙级的累计用量记在那条工具结果消息的 `subAgentUsage` 上。求和用 `sumUsage()`：一段会话里所有消息的用量累加，就是它的实际消耗。

## 代价

`self` 方式交接本身要多跑 1~2 次全量输入：那一次的输入比平时长。它换掉的是一份会持续增长的历史，但这一笔开销是真实的，不会因为它是「交接」而消失。

`summary` 方式便宜、确定，但没有原会话上下文也没有工具，保真度低。它不会自动顶替失败的 `self` 交接——把「模型没写出文档」当成「换个人接着写」，会让一次失败的交接看起来像成功。
